# Development

**In short:** this page is for people who change lore itself. It shows how the code is laid out, how to build and test it, and how a new version is released. If you only use lore, you do not need it.

Internal build / release notes. End-user docs live in the top-level [README](../README.md).

## How it works

| Layer | Detail |
|-------|--------|
| Storage | committed `_v: 2` JSON row files under `.lore/data/` are the truth; a SQLite cache (pure-Go `modernc.org/sqlite`, `adapters/cache/sqlite`) is built from them at run time; machine-local tables live in `~/.lore/state/machine.db` |
| Sync | `adapters/live`, `adapters/reposync` and `ops/sync` carry rows between the working tree, the live ref and the store; row merge in `logic/merge`, `logic/merge3`, `logic/canonjson`; design in [LORE_SYNC_SPEC.md](../LORE_SYNC_SPEC.md) |
| Search | SQLite FTS5 (built into the binary) + hybrid ranking |
| Output | Compiles stored knowledge into `CLAUDE.md` / `AGENTS.md` / `.cursorrules` |
| Agent loop | The lore skill (an instruction file the coding agent loads) captures corrections & decisions back into the db |

## Layout

One Go module, `github.com/thesatellite-ai/lore`, at the repo root (no `go.work`; a clean clone builds from the module proxy). The packages are layered (`model`, `schema`, `logic`, `store`, `adapters`, `op`, `engine`, `ops`, `surface`, `wire`, `app`, `cmd`); `internal/layers` fails the build when a lower layer imports a higher one.

| Path | Role |
|------|------|
| `app/` | the `lore` command itself: `app.Main` / `app.Run(ctx, args, ...Option)`, every host command and its tests. Importable, so another build composes the same command with options (`WithVersion`, `WithSetupUI`) instead of swapping files; only `cmd` may import it (`internal/layers`) |
| `cmd/lore` | the `lore` binary's `main`: stamps the version and calls `app.Main` with no setup UI, so `lore setup web` serves the plain page (`setupweb.DefaultUI`) |
| `wire/` | the composition root: picks the concrete backends, cache, scanner and identity |
| `surface/cli`, `surface/rest`, `surface/tui`, `surface/docs` | CLI, local REST + OpenAPI (`lore api`), the TUI, and the generated reference |
| `ops/<noun>` | one package per noun, each defining its operations |
| `adapters/backend/{git,folder,rowfs}`, `adapters/cache/sqlite` | store backends and the run-time SQLite cache |
| `tests/teame2e` | the team end-to-end suite (`task lore:test:team`, build tag `teame2e`) |
| `tests/setupe2e` | the setup page end-to-end suite (`task lore:test:setupe2e`, build tag `setupe2e`): fake machines and the real `lore setup web` |
| `tests/journeys` | the real-user journeys (`task lore:test:journeys`, build tag `journeys`): personas living with lore over months, shared invariants after every step ([tests/journeys/README.md](../tests/journeys/README.md)) |

The v0.1.17 modules `saas/`, `dbent/`, `lace/` and `go.work` were deleted in phase E (42dbef7a).

## Engine notes (0.1.18 core)

Every row write in the core goes through one path in `engine/`: scan, validate, policy, backend, cache, audit. Two context helpers in `engine/batch.go` change how a group of writes lands; an operation that writes many rows as one action uses them instead of its own loop of commits.

| Helper | What it does | Who uses it |
|---|---|---|
| `engine.Staging(ctx)` then `engine.Commit(ctx)` | Every engine write made with the staged `ctx` is held, not written. `Commit` writes all of them as one backend batch (one git commit on a git store), then refreshes the cache and records the audit. All or none: a failed write leaves the store as it was. A stage that touches two stores is refused with `E_INVALID_INPUT` and nothing written. A second write of the same row inside one stage is `E_INVALID_INPUT` (the stage cannot read its own rows back); a repeated create of the same row (an actor row two writes both ensure) is dropped. After `Commit` the stage is closed: a later write with the same `ctx` goes straight to the store. | `lore resource import` (FB-RES-1): the whole file is one batch, one commit |
| `engine.WithCreateID(ctx, id)` | The next `Create` of a row of `id`'s table made with `ctx` uses `id` instead of a fresh one. It runs through the ordinary `Create` path, so every guard a surface adds around `Create` still runs; creates of other tables (an actor row the write ensures) are not affected; the row must not exist yet (`E_STALE`). | `lore resource import`: each new row's id is pinned first, so references between rows of the same file resolve before any row is written (no second pass) |

`vendor/` is **not** committed; `go.sum` is. A fresh clone builds from the module proxy. The build is pure-Go: `CGO_ENABLED=0`, `modernc.org/sqlite` (FTS5 is built in — no build tag).

## Build

Requires Go 1.26+ and [Task](https://taskfile.dev/).

```sh
task lore:build          # → tmp/bin/lore (version stamped from git describe)
task lore:build:debug    # with debug symbols
task lore:install:all    # build + install binary AND the lore skill locally
task lore:skill:install  # (re)install the skill to ~/.claude/skills/lore
task lore:test:quick     # QUICK tier: every unit test, Go test cache on, no race, no e2e (run it all the time)
task lore:test           # every package plain + the concurrent packages under the race detector
task lore:test:race      # only the race set (RACE_PKGS in Taskfile.lore.yml)
task lore:test:sync      # git-sync tests: row merge, the live ref, branch sync, sync operations
task lore:test:team      # team end-to-end suite (real binary, real git, many actors)
task lore:test:setupe2e  # setup page e2e: every machine shape via the page's HTTP API
task lore:test:cover     # coverage of unit AND end-to-end tests; lists functions no test reaches
task lore:check:gocache  # trim Go's build cache (idle entries) when it is over LORE_GOCACHE_MAX_GB (default 50)
```

### Test builds are not version-stamped, and the Go cache is bounded

Every task in `Taskfile.lore.yml` runs Go with `GOFLAGS=-trimpath -buildvcs=false` (its top-level `env:`; a `GOFLAGS` you export yourself wins), and the test helpers that `go build` the binary (`tests/machines`, `tests/journeys`, `tests/setupe2e`, `tests/teame2e`, `tests/userscen`) pass the same two flags. Why: a package compiled without `-trimpath` records the folder it was built in, and `-buildvcs` stamps the commit and dirty state into `cmd/lore`, so each of the ~30 worktrees on one build server compiled every package again and every commit added new cache entries; the shared Go build cache (`go env GOCACHE`, one per user) reached 1.2 TB and filled the disk. With the flags, the same code in two worktrees is one cache entry: building `cmd/lore` in a second copy of the tree added 208 MB to the cache without them and 3 MB with them (measured 2026-11-10). Test binaries carry the version `dev` (cmd/lore's default; `formatgate.DevBuild` treats it as a source build). The gate's build stage builds `tmp/bin/lore` with `lore:build:test` (version `dev`, no VCS stamp). Only `task lore:build` (and so `lore:install`) stamps the real version from `git describe` and keeps the VCS stamp, and the binary release stamps the release version through the same ldflag.

Nothing else bounds the cache (Go drops entries unused for 5 days, which does not help when every worktree builds every day), so `task check` starts with `lore:check:gocache` (`tests/lib/gocache-trim.sh`): it measures `go env GOCACHE` with `du` (about 4 s on a 570 GB cache) and, only when the cache is over `LORE_GOCACHE_MAX_GB` (default 50), deletes the entries no build has used for `LORE_GOCACHE_IDLE_MIN` minutes (default 120; Go refreshes an entry's time when a build uses it, so such an entry is in no running build). It never empties the whole cache: `check:fast` and the quick tier take no lock and may be building at that moment, and `go clean -cache` failed those builds and itself ("directory not empty"). A file that vanishes or appears meanwhile is not an error; if recent builds still hold the cache over the limit it says so and the next gate trims again. `LORE_GOCACHE_TRIM=dry` only says what it would do, `LORE_GOCACHE_TRIM=off` skips the step. It touches nothing but the cache folder, never a tracked file.

## The setup page (`surface/setupweb`)

- **Server.** `surface/setupweb` owns the local page server: one-time token, session cookie, CSRF header, Host and Origin checks, the CSP and the allowlisted `/v1` routes. The page's files come from a `setupweb.UI` (`FS()` with `index.html` and `assets/`, plus a content-hash `Version()`). This build hands in no UI, so the server serves `setupweb.DefaultUI`, a plain page that names the serving binary (its version and resolved path, filled in by the server at serve time; no script), says how to open the guided page with the released lore, and lists `lore setup plan|check|apply` and `lore doctor --all`. Another UI can be handed in through `setupweb.Options.UI` without changing the server's security rules; open packages never import code outside this module's layers (`internal/layers` enforces it).
- **Serving.** `GET /setup/assets/{file...}` serves `.js`, `.css`, `.svg`, `.woff2`, `.png` and `.txt` files from the UI's `assets/` (anything else is 404); every other `GET /setup/...` path except `assets`, `session` and `close` answers `index.html`, so a UI can route with history URLs under `/setup/`. The CSP allows `'self'` only, with no `'unsafe-inline'`, so `index.html` must not carry an inline script or style.

## Two test tiers

| Tier | Command | When | What runs |
|---|---|---|---|
| quick | `task lore:test:quick` | all the time while building: after every edit, before asking for review | `go test ./...`: every unit test of the root module with Go's test cache, no `-race`, no end-to-end suite except the fast machine shapes (`tests/machines` `TestForeign|Env|Links|Shapes`, about 45 s, skipped when arguments narrow the run). Narrow it with `task lore:test:quick -- ./ops/task/...`. Not behind `testlock`, so it never queues behind someone's full gate |
| fast | `task check:fast` (= `task lore:check:fast`) | landing a small fix (see "Landing" below) | a quick sanity check: build, vet, gofmt, staticcheck, cross-builds, tidy and every unit test (the layer and no-any guards are unit tests); no race detector, no end-to-end suite and no docs step (the full gate after landing runs them); about 2-3 minutes. Not behind `testlock`: it never queues behind someone's full gate |
| full | GitHub Actions `gate.yml` (locally `task check` = `task lore:check`) | on every push to `dev` and on demand for any branch or commit; every release waits for it on the exact release commit | everything below: every step of `GATE_STEPS` as its own job, plus the docs index and the recall report |

**Where the full gate runs.** The full gate runs on GitHub Actions, not on a shared machine: `.github/workflows/gate.yml` starts on every push to `dev` and on demand (`gh workflow run gate.yml --repo thesatellite-ai/lore --ref <branch>`, add `-f ref=<commit>` to test another commit). Pushes to `dev` share one concurrency group: the run already going finishes, and of the pushes that arrive meanwhile only the newest waits (GitHub cancels the older pending run), so a burst of landings tests its newest commit next instead of queueing one full matrix per push; a commit whose run was skipped that way has no verdict of its own, and a release takes a commit whose run finished green. Its `steps` job reads `GATE_STEPS` from `Taskfile.lore.yml` (`tests/lib/gate-matrix.sh`), so a step added there runs on Actions with no workflow edit; the `warm` job compiles the module once into a cached Go build cache; then every step runs as its own job on a plain ubuntu runner (`tests/lib/ci-step.sh`: the step's task, its log, and a check that it left the tree clean), with `fail-fast: false`. The `docs-index` job re-runs the docs examples and the commands index and fails when a transcript or index differs from the committed one; the `recall` job runs the recall benchmark as a report that never fails the run. The final `summary` job writes PASS, FAIL or NO RESULT and the wall seconds of every step into the run's summary page and fails when any step failed, so the run's conclusion is the gate's verdict; a failed step's log is an artifact of the run (`gate-log-<step>`). The run's title is `Gate <commit>`; releases look for that run and its `summary` job (`internal/repoguard` `TestActionsGateRunsEveryGateStep` pins the shape). The quick and fast tiers stay local. Every step must pass on a plain runner: no dependence on a particular machine's paths, tools, test lock or agent environment; the Taskfile takes `testlock` only when it is on PATH and sizes `GATE_SLOTS` from the cores when it is not set.

Measured on a 48-core Linux machine: the quick tier takes about 48 s with an empty test cache (slowest packages wire 38 s, ops/settings 29 s, app 26 s, ops/task 21 s; 2026-11-07) and less when most packages are cached. The full gate took 1526 s on 2026-11-11 with every end-to-end suite started at once (a load average of 161, peaks above 300, 42 % of the CPU spent in the kernel switching between processes); the same steps scheduled under the load budget, with the docs, scenario and chaos runners in parallel and `wire`'s race tests in shards, take about 15 minutes (below).

The quick tier stays fast only while no unit package is slow: a package that takes minutes is a test-design bug, not a reason to drop it from the tier: time it with `go test -json`, then make it fast without weakening it (independent tests `t.Parallel()` with their own temp dirs, fixtures and binaries built once per package, events or short deadline polls instead of sleeps). The end-to-end suites are behind build tags (`userscen`, `teame2e`, `setupe2e`, `machines`, `journeys`) or are shell/node runners, so `go test ./...` never starts them.

A unit test gives the same result in every shell: a Go test binary drops the agent markers, identity overrides and `USER` / `USERNAME` it inherited and detects no agent from the process tree (`wire/detect_testbinary.go`), so a test that needs a person or an agent sets one itself (a git identity in the test's HOME, `LORE_HUMAN`, cliWorld's `claude()`). The journey and team World (`tests/teame2e/teamharness`) runs lore with `USER` and `USERNAME` set to its fixed OS user `tester` on every simulated machine, so the OS-user step of the identity chain answers the same from any shell. `LORE_TEST_AMBIENT_AGENT=1` keeps the shell's agent for a run by hand.

## Test time limits

Every limit on how long a whole run may take was tuned on the 48-core Linux gate server; a 10-core Mac runs each step 3-5x slower, and the steps died at their 15/20/40/60 minute limits with nothing wrong. One factor stretches all of them: `LORE_TEST_TIME_SCALE` when set (a number >= 1, for example `LORE_TEST_TIME_SCALE=4 task check`), else computed from the machine as `max(1, 48 / cores)` capped at 6, times 1.5 on macOS. It is 1 on the gate server, so the limits there are unchanged; a 10-core Mac gets 7.2, a 24-core Linux machine 2. A value that is not a number >= 1 is refused, never ignored.

What scales: every `go test -timeout` in the Taskfiles (the gate steps call those tasks; a `go test` that named none got Go's fixed 10 minutes and now names it), written `-timeout $({{.TEST_TIME}} 40m)` (`tests/lib/testtime.sh`, which prints the scaled limit); the harness waits for a slow process or a whole run in `tests/*` and in unit tests (a lore run's deadline in teamharness, the machines and setupe2e run and page deadlines, "printed no link/listening line" waits, deadlock and hang guards), through `testtime.Scale(d)` (`internal/testtime`); and the shell runners' waits (`testtime_secs` in the docs runners, the chaos and scenario scripts). `TEAMHARNESS_CMD_TIMEOUT` and `ANSWER_TIMEOUT`, when set, are used as given.

Product speed bars scale too, through `testtime.SpeedBar(d)` ("doctor --all within its budget", "adopting 5,000 rows under a minute", the p95 of agent commands, "a 20 MB binary is checked in under 2 s"): at factor 1 each is exactly as written, so the gate server still catches a real slowdown, and on a slower machine it stretches like every run limit, so a laptop does not fail it for being a laptop. How fast lore's everyday commands are on a given machine is measured separately, not by these bars.

What does not scale: a timeout that is the behaviour under test (lock waits, fetch and probe timeouts, back-off, TTLs and leases, a server's shutdown timeout, a "did not finish in 700ms" stop, a kill at a deadline), a check that a stamped time is "now", and git-run counts. Scaling those would hide the very failure they test.

Guards (`internal/testtime`): the factor is 1 on a 48-core Linux machine and is applied to a sample deadline, the shell helper computes the same factor as the Go one, no Taskfile or test script passes a raw `-timeout` or `timeout N` or runs `go test` without a `-timeout`, and every test that compares a measured time with a literal or a `…Budget` either goes through `testtime.SpeedBar`/`Scale` or is listed, with its reason, as a behaviour bound (`TestSpeedBarsScale`).

Each gate part must also fit its limit with room to spare, or it dies with tests never started (devco D-779: the journey catch-all ran about 210 journeys at `-parallel 2` in 15 minutes and stopped with about 85 never started, so no gate ran them for a day). `tests/lib/gate-test-times.tsv` holds the measured wall seconds of every journey and story test and whether it runs in parallel; `internal/repoguard` `TestGateStepsFitTheirTimeout` (a unit test, so both gate tiers run it) adds up every gate part on those suites the way go test schedules it (serial tests one after another, then the parallel ones `-parallel` at a time, but never more at a time than the cores of the part's `GATE_STEPS` line, the share of the load budget the gate gives it), multiplies that by the part's gate slowdown (how much slower than counted it really ran in a full gate: its suite's `gateSlowdown`, 3.4 for the stories after devco D-811, where on a box at load 154 the stories catch-all counted at 266 s took 891 s of its 900, or the part's own `stepSlowdown` where a gate measured it far from its suite's, 1.5 for story WW's two matrices, whose places already run side by side; a split or new part counts at its suite's factor until a gate measures it, and the guard fails when a `stepSlowdown` name is no longer a gate step) and fails when a part needs more than 70 % of its `-timeout`, counting a test with no row at its suite's mean; it also fails when more than half of a part's tests have no row (devco D-783: the persona parts were never measured and the mean said 2 minutes for a part that took 6), so a new part is measured with its own `go test -json` run before it lands. When it fails, split the part (another `test:<suite>:<part>` task with its own `-run`, a `GATE_STEPS` line, and its pattern in the catch-all's `-skip`) or raise its `PARALLEL` together with its cores where the tests allow it; never only the timeout. After a full gate, compare each part's wall time (`tmp/check/timings.tsv`) with the estimate `go test -v -run TestGateStepsFitTheirTimeout ./internal/repoguard/` prints, and raise the suite's `gateSlowdown` (or the part's `stepSlowdown`) when a part ran slower than counted. Re-measure after adding many tests: run the suite with `go test -json` (for example `go test -tags journeys -count=1 -json -parallel 2 ./tests/journeys/ > /tmp/journeys.json`) and record it with `tests/lib/test-times.sh tests/journeys /tmp/journeys.json`.

## Paths: one rule for comparing and storing them

The same folder can be spelled two ways: on macOS every temp folder sits under `/var`, a symlink to `/private/var`, so `$TMPDIR`, `t.TempDir` and a person's `$PWD` say `/var/...` while `git rev-parse` and resolved paths say `/private/var/...`. `model/fspath` is the one rule: store a path canonically when it will be compared later (records, map keys, lock owners) with `fspath.Canonical`, and compare with `fspath.Same`, `fspath.Within` or `fspath.Rel`, never with `==`, `strings.HasPrefix` or a bare `filepath.Rel` across two sources. Output never rewrites what the person typed; a folder lore derived from their path is echoed in their spelling with `fspath.InTyped`. The packages that compare paths most (`adapters/backend/rowfs`, `wire`, `wire/host`, `wire/renderhost`, `app`, `logic/origin`, `tests/teame2e`) run their tests with `$TMPDIR` behind a symlink (`internal/testenv.LinkTemp` in their `TestMain`), the macOS shape on Linux, so the gate catches a path compared the old way.

## Journeys: every feature adds its steps

A feature that changes what a person does over time (a new command, a new kind of store, a new sync mode, a new refusal, a new setup step) adds, in the same change, the journey steps where a real person would meet it, in the persona who would (`tests/journeys/<persona>_test.go`). A rule that must hold everywhere becomes a shared invariant instead. How: [tests/journeys/README.md](../tests/journeys/README.md).

## Every scenario and every bug is a replayable regression

A story is one scenario lore was tried against, written down so it can run again: who the people are, what they do in plain words, and what must hold afterwards (`tests/stories/<id>-<name>.md`), plus a hermetic Go test that replays it end to end with the real binary. Every finding ever fixed has a row in `tests/stories/REGRESSIONS.md` naming the test that guards it, and a guard test fails when a row names a test that does not exist or a finding has no test. The stories run in the full gate (`task check` and `task check:after-land`, in nine steps: `stories-ww-writes` and `stories-ww-stand` run story WW's two matrices (`TestStoryWWWrites`, `TestStoryWWhereYouStand`, the suite's longest tests) each alone with its places in parallel, `stories-ww` the other WW tests, `stories-an` the stories A to N after `TestStory` but the landings BL, `stories-bl` the landing stories BL, `stories-o` and `stories-oz` story O (the owner-shaped machine; `stories-o` its stories named A to N, `stories-oz` the rest), `stories-wuct` the W stories WU and WCT, and `stories` every other story), not in `task check:fast`.

Every new scenario, bug fix or feature lands with its story, its test and its REGRESSIONS.md row in the same commit, or it does not land. How: [tests/stories/README.md](../tests/stories/README.md).

## The gate: `task check`, before every push

`task check` holds the machine-wide `testlock` for its whole run, first bounds the Go build cache (stage cache: `lore:check:gocache`, above), compiles the module once (stage warm: `lore:build:warm`, plain and `-race`, so the steps that follow find every package in the cache instead of each compiling the same code at the same time), builds the test binary (stage build), then runs every check in one stage, test. Each step writes its own log to `tmp/check/<step>.log`; when a stage ends it prints every step's wall seconds and CPU seconds so far and each stage's wall time with its peak and mean load average (`tmp/check/timings.tsv`, `stages.tsv`). A failed step fails the stage, is named, and the tail of its log is printed. A stage starts only when the one before it passed.

**The load budget.** The steps of stage test are listed once, in `GATE_STEPS` in `Taskfile.lore.yml`: each with the cores it keeps busy on average (its CPU seconds over its wall seconds in a measured gate, at the `-parallel`, `JOBS` or `SHARDS` it is given) and heaviest first. `tests/lib/gate-parallel.sh` starts them in that order while their cores fit `GATE_SLOTS` (default five sixths of the machine's cores, 40 of a 48-core server; `GATE_SLOTS=12 task check` sets it), so the load stays near the core count instead of every suite fighting for the CPU at once. Every lore process the end-to-end suites start gets the Go runtime settings of `LORE_E2E_GOENV` (default `GOMAXPROCS=2 GOGC=off GOMEMLIMIT=512MiB`; the harnesses add them through `tests/e2eenv`, the docs runners through `envfor`): a lore command lives a fraction of a second, and sized by Go for all 48 cores it spent about 40 % of its CPU on garbage-collector workers and idle scheduler threads. The settings change what a run costs, never what lore does; only lore processes get them (the Go toolchain and the test binaries keep Go's defaults). Outside the gate a lore process paces its own collector for a short run (`app/gcdefaults.go`: GOGC 400 with a 2 GiB soft memory limit, about a third less CPU per command), and a GOGC or GOMEMLIMIT in the environment (the gate's included) wins. Each suite names its `-parallel`.

**Where the time goes.** The gate is bound by CPU, not by any one step: the end-to-end suites start about 100,000 lore processes, each about 0.2 CPU seconds (building the operation registry by reflection, opening the SQLite cache, 40 to 60 git subprocesses), about 28,000 CPU seconds in all; at 40 cores that is close to 12 minutes however the steps are arranged. Making the gate faster now means making a lore command cheaper or a suite run fewer of them without testing less; the timings table names the heaviest steps (userscen, setupe2e, machines, sweep-rest, teame2e).

Run one step on its own with its task name (`task lore:test:team`, `task lore:test:setupe2e`, `task lore:scenarios`, …); the public names of the heavy suites take `testlock` themselves when it is installed.

```sh
task check               # alias of task lore:check
task lore:hooks:install  # once per clone: use the committed .githooks
```

`task lore:hooks:install` points git at `.githooks/`, whose `pre-push` hook enforces the gate. A passing `task check` records the tree of the tracked files it tested (`.git/lore-check-passed`). On `git push`, if every pushed commit has exactly that tree, the push goes through at once; otherwise the hook runs `task check` first and blocks the push if it fails, or if the code it tested is not the code being pushed (uncommitted changes while checking). `git push --no-verify` skips it, for emergencies only. The hook itself is tested in `internal/repoguard/prepush_hook_test.go`.

This repository is public, so client, company and people names and private host names never go into it: tests and docs use made-up names (acme, alice, bob). The list of such words is private and never committed in any form (not even hashed: a hash of a short name is reversed in seconds). Each maintainer keeps it on their own machine at `~/.config/names-guard/terms.txt` (mode 0600; `NAMES_GUARD_FILE` points elsewhere): one term per line, `#` starts a comment, a term may hold `.`, `@`, `-` and spaces. `bash tests/lib/names-guard.sh --files` checks every tracked text file and path, `--messages <revs>` the author, committer and message of each commit, `--added <revs>` the lines each commit adds, `--stdin` any text; a hit is a whole word, case-insensitive (letters, digits and `_` are word characters), and the report names the file and line or the commit, never the word. The `pre-push` hook runs it on every commit being pushed, and `internal/repoguard` `TestNoListedNamesInTrackedFiles` runs it on the tree. Where no list exists (GitHub Actions, other contributors) it prints `names-guard: no list at <path>, skipped` and passes. Generic words that may be on someone's list but are fine here go in `tests/lib/names-guard-allow.txt`.

### Landing: `check:fast` for a small fix, the full gate on main

A small fix (a policy tweak, a message, one function and its test) need not wait for the full gate. The rule:

1. Run `task check:fast` on the fix. It is a quick sanity check, not the real gate: build, vet, gofmt, staticcheck, cross-builds, `go mod tidy -diff` and every unit test, about 2-3 minutes. It takes no machine-wide `testlock` (only the full gate does) and so runs no Go build cache trim, and it runs no race detector (the full gate's race steps do). It runs no end-to-end suite (userscen, the team suite, the setup page suite, the machine suites and their sweeps and life parts, the journeys, scenarios, chaos) and no docs step (the docs examples, docsync) and not the Windows and macOS test compile (`build:cross:tests`): with them it took 22 minutes on the shared server. `FAST_MAP` in `Taskfile.lore.yml` (`tests/lib/fast-plan.sh` reads it) maps changed paths to end-to-end steps and names none today; a narrow step a path really needs can be named there again if the tier still fits. It writes its own stamp, `.git/lore-check-fast-passed`, and the pre-push hook accepts either stamp for the exact tree being pushed. Its summary prints every step's wall and CPU time and the total. `SKIP_DOCS=1` is still accepted and changes nothing; setting `FAST_MAP` or `FAST_UNIT_STEPS` on the command line has no effect, they are vars of the included `Taskfile.lore.yml`.
2. Push. Then run the full gate on what landed: `task check:after-land` fetches origin, makes a fresh worktree of `origin/main` in a temp folder, runs `task check` there and writes the result to `LORE_GATE_REPORT` (default `~/.local/state/lore-gate/last.md`): first line `PASS <commit> <subject>` or `FAIL …`, then the step timings, with the step logs beside it.
3. The full gate after landing is the real gate: every end-to-end suite and the docs steps run there. On `dev` it runs by itself: every push to `dev` starts the Actions gate ("Where the full gate runs" above). A `FAIL` there is fixed in the next change, before anything else lands.

A release is never cut on `check:fast`: the release commit itself passes the full gate, the Actions gate run on that exact commit ("Releases" below; the binary release has the same rule).

No gate step may modify tracked files: `task check` records the tracked tree when it starts (`check:begin`) and refuses to stamp if it changed by the end, naming the files. That is why `check:docs` (`tests/lib/check-docs.sh`) puts the whole `.ds/` folder back as it was after `ds scan`, which rewrites `ledger.tsv` and `refs.tsv` (their header records the commit and time of every scan) and adds a block file for every changed block: run `ds scan` and `ds ack` yourself and commit when docs or citations change. Uncommitted changes to tracked files also make the stamp differ from the commit being pushed, so commit or `git stash` them before pushing.

### Setup page end to end: `task lore:test:setupe2e`

`tests/setupe2e` (build tag `setupe2e`) builds a fake machine per shape: gh logins (0, 1 or 2, which one active), `~/.ssh` (none, the default key only, several Host aliases, an alias whose key is missing; keys with or without `.pub`), `~/.gitconfig` includeIf identities, the state of `~/.lore` (empty, a v0.1.17 install, saved, removed, disabled or trashed setups, an invalid `config.yaml`) and the start folder (a lore repo, a git repo, a plain folder). Fake `gh`, `ssh` and `git` log every call with the account it acted as, a fake GitHub API answers `LORE_GITHUB_API`, and bare repos stand in for GitHub; logins, emails and keys are placeholders made at run time. `TestAPIMatrix` runs all 1764 valid shapes through the real binary's HTTP API (token, cookie, CSRF), saving every step with the page's own defaults, and fails when a refusal names a value lore filled in, when Save is refused for anything but a value only the person can give, when a gh or ssh call for a GitHub account's repo runs as another account, or when `config.yaml` lacks the setup; an invalid `config.yaml` must come back as typed problems instead. A world or server that cannot start fails the shape; nothing skips.

One world by hand, for a debugger: `go run -tags setupe2e ./tests/setupe2e/cmd/setupworld up --shape '{"gh_accounts":2,"gh_active":"second","ssh":"several","keys":"with_pub","include_if":1,"lore_home":"setups","start":"plain"}' --dir <empty dir> --port <port>` prints one JSON line (the setup link, HOME, config and log paths, accounts) and serves until Ctrl-C. `SETUPE2E_ONLY=<part of a shape name>` narrows the matrix. `SETUPE2E_SHARD=<i>/<n>` runs every n-th shape starting at the i-th (the gate's parts); a malformed value fails the run.

Adding a table? Declare it once with `schema.Table(...)` in `schema/` (a synced row table or a machine-local one); that one definition drives the cache tables, foreign keys, indexes, CLI flags, REST routes and the docs. There is no code generation.

Plain `go build`:

```sh
CGO_ENABLED=0 go build -o tmp/bin/lore ./cmd/lore
```

## Composing the binary (package app)

All of the `lore` command lives in package `app`; `cmd/lore/main.go` is three lines that stamp the version and call `app.Main`. Another build composes the same command by importing this module and passing options, never by copying or swapping files:

```go
import "github.com/thesatellite-ai/lore/app"

func main() { app.Main(app.WithVersion(version), app.WithSetupUI(myUI)) }
```

| API | What it does |
|-----|--------------|
| `app.Main(opts ...Option)` | the whole process: the session-end hook fast path, an interrupt-cancelled context, `Run` over `os.Args`, `os.Exit` |
| `app.Run(ctx, args, opts ...Option) int` | builds the app and the command tree, runs `args`, returns the exit status |
| `app.WithVersion(v)` | the version the binary reports (empty keeps `dev`) |
| `app.WithSetupUI(ui)` | the static files `lore setup web` serves (`setupweb.UI`: files only; routes, headers and operations stay the core's). Without it the page is `setupweb.DefaultUI`, the plain page naming the CLI commands |

An enterprise build can add a setup page through `WithSetupUI`. Only `cmd` may import `app` (`internal/layers`), so no core package depends on how the binary is composed. `TestRunAppliesOptions` (app) checks the options and `TestBinaryServesDefaultUI` (tests/setupe2e, in `task lore:test:setupe2e`) checks that this module's binary serves the fallback page.

The test harnesses under `tests/` are ordinary packages, so a build that imports this module can reuse them: `tests/setupe2e` (build tag `setupe2e`; `Build`, `World.Start`, `World.HangProfile`, `PairwiseShapes`) and its world tool `go build -tags setupe2e github.com/thesatellite-ai/lore/tests/setupe2e/cmd/setupworld`.

Changing this module and an importing build together: keep both clones side by side and put a `go.work` in a separate folder above them (`go work init ./lore ./<other>`), or add a local `replace github.com/thesatellite-ai/lore => ../lore` that is never committed. This repo has no `go.work`: a clean clone builds from the module proxy. Land the change here first, then move the importing build's `require` to the new version.

## Releases

This repository publishes no binaries. A release of the core is a version tag on `dev`, made by `.github/workflows/release.yml` dispatched on the `dev` ref: `gh workflow run release.yml --ref dev -f tag=vX.Y.Z` tags `dev`'s head at that moment. Releases are built from `dev`; nothing is squashed into `main` any more (`main` stays where it is, and a push to `main` without `[skip release]` in the commit **subject** still makes the next patch tag there).

Every fix in the tagged commit landed on `task check:fast` with its own story ("Landing" above), and the release waits for the Actions gate (`gate.yml`, "Where the full gate runs" above) to pass on the exact commit it tags.

No binary is built here and the workflow creates no GitHub Release. The tag is also the Go module version an importing build requires, so a tag is permanent: never move or reuse one, fix forward with the next version.

The released `lore` binary (this core plus proprietary components such as the guided setup page) is built and published separately, at the same version, after the tag exists: it cross-compiles linux/darwin/windows × amd64/arm64 and uploads per-platform archives named `lore_<os>_<arch>` (`.tar.gz`, `.zip` on Windows) with `checksums.txt` to this repository's GitHub Release for the tag, so `lore upgrade` (`adapters/selfupdate`), `install.sh` and `install.ps1` keep reading releases from here. Every archive holds `lore` (`lore.exe`), this repository's `README.md` and `skills/`, `BINARY-LICENSE.txt` (the binary's terms: free to use, commercial use included), `LICENSE-core-Apache-2.0` and `NOTICE-core` (this repository's `LICENSE` and `NOTICE`). The source here stays Apache-2.0; a binary built from it (`task lore:build`) is Apache-2.0 alone and serves the plain setup page.

## Homebrew tap

Homebrew entries for all `thesatellite-ai` tools live in one shared tap repo: **`thesatellite-ai/homebrew-tap`**. The binary release writes the formula `Formula/lore.rb` there (goreleaser `brews`), pointing at the archives on this repository's Releases; users run `brew tap thesatellite-ai/tap` and `brew install lore` (or `brew install thesatellite-ai/tap/lore`), on macOS and Linux. The formula installs only the binary, so users add the agent skill once with `lore skill install --all`; after a `brew upgrade` the first lore command refreshes it. A formula install lives under `<prefix>/Cellar/lore/<version>/` (a cask install, should the tap move to one, under `<prefix>/Caskroom/lore/<version>/`); `lore upgrade` treats both as Homebrew installs and runs `brew upgrade`. Nothing in this repository writes to the tap.
