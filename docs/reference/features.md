# Feature index

**In short:** this page lists everything lore can do, one row per feature, grouped by area. Each row says in one plain line what the feature is for, where its code lives, which guide explains it, and which runnable example shows it. Use it to find the right page fast, or to check that a feature exists before you go looking.

How to read the columns:

- **Feature**: the command, flag, config key, environment variable or error code.
- **Package**: the Go folder that holds the code, so you can read it yourself.
- **Guide**: the best page section that explains the feature. A guide marked *(brief)* only mentions the feature there; "—" means no guide covers it yet.
- **Example**: where you can see the feature used. `docs example` and `team example` sections run the real lore binary in throwaway folders: `docs example` links open a section script under `tests/docs/sections`; `team example` links open the output of a section in `tests/team/docs/run-examples.sh`; `test SC-n` and `test CH-n` are test scripts under `tests/`; a walkthrough is a step-by-step page in `skills/examples` whose commands are checked but not run. "none" with a reason means the feature cannot be shown by a command run.

Words used on this page, in plain terms:

- **Row**: one note lore keeps, such as a rule, a memory, a decision or a task.
- **Live row**: a row everyone sees at once, before any commit. Lore keeps live rows on a hidden list on the git server that is not a branch (git calls it a *ref*), and copies finished ones to main.
- **Org**: a company you work for, set up in your own `~/.lore/config.yaml`.
- **Store**: a separate notes-only repo that only your company can open. Anything in the client's repo, on any branch or hidden list, the client can download, so the agency keeps its private notes in its own store, for example `github.com/agency/notes`.
- **Claim**: an agent saying "I am working on this task". It runs out unless the agent renews it, so a stuck agent never blocks a task for long.
- **Render**: writing your notes into `.lore/LORE.md` and pointing the file each coding tool reads when it starts (AGENTS.md, CLAUDE.md, GEMINI.md, a Cursor rule, ...) at it.

The commands were collected from `lore --help` of the current build (every command has its own row, or is listed as a verb of its group), the config keys from `logic/orgconf`, the environment variables from the code, and the error codes from `model/errs/codes.go`. Run `lore <command> --help` for every flag of a command.
