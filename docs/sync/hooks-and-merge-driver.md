# Hooks and the merge driver

**In short:** lore adds a few short lines to your repo's git set-up so notes stay safe without you thinking about them. A *merge driver* (a small helper git calls to combine two edits of the same note) merges them field by field. A few *hooks* (small scripts git runs at fixed moments, like before a commit) check note files before you commit them and read new notes in after a pull. lore sets all of this up by itself and never takes over hooks you already have.

## What it is and when you want it

git lets a repo plug in its own tools at two places:

- **Merge drivers:** a program git calls instead of its normal line-by-line merge for certain files. lore's driver knows that a note file is a list of fields, so it can keep the change Alice (an agency developer) made to one field and the change Bob (another agency developer) made to another (see [Conflicts and duplicates](conflicts-and-duplicates.md)).
- **Hooks:** scripts in `.git/hooks` that git runs before or after a commit, checkout, merge or push. They are never shared by `git clone`; each clone has its own.

lore sets both up on its first command in a clone and checks them, quickly, after every command. You want this page to know what was added to your repo, to check it, or to understand why a commit was refused.

## Before you start

- A repo set up with lore ([How notes travel with git](how-notes-travel-with-git.md)). Here Alice works in `github.com/client/website`.
- If your team uses a hook manager (a tool that shares one set of hooks with the whole team: husky, lefthook, or a committed `.githooks` folder), lore adds its lines to the hook scripts already there. When that folder is part of the repo (husky's `.husky`, a committed `.githooks`), a lore command never creates a hook file in it and never adds its lines to the team's own hook files there, because a new or changed file there reaches every teammate: it says which hooks it left alone, `lore init` and `lore doctor --fix` and plain `lore fix` leave it alone too, and only `lore fix --tracked-hooks` (your explicit yes) writes them and tells you to commit them (or undo them). Every line that says lore's hook blocks there are missing or older than your lore (the commit's check, `lore doctor`, the leak-guard warning) names `lore fix --tracked-hooks`, never `lore sync`, since a sync leaves that folder alone too. `lore doctor` there prints the exact lines to paste into your own hook files instead (each block with its `# >>> lore-sync … >>>` markers; pasted as printed, lore finds its block and stops warning). Linking a client repo whose hooks folder is committed writes nothing there either: `lore org link` prints the `commit-msg` lines to paste. Hook files an older lore left in such a folder that git does not track and that hold nothing but lore's blocks show in `git status`; `lore doctor` names them and `lore doctor --fix` removes them (a file with any line of your own stays, and so does a file `lore fix --tracked-hooks` created at your request until you commit it). To keep lore's hooks on your machine only, copy the folder's hooks into `.git/hooks`, run `git config --local core.hooksPath .git/hooks`, then `lore fix`. In a project whose `.lore/` folder git ignores, lore never writes into a committed hooks folder at all. A folder git ignores (husky 9's `.husky/_`), or one with no committed file in it, is not part of the repo, so lore writes there as in `.git/hooks`.

## Step 1 — See what lore set up

lore does the set-up after every lore command, so there is no command to run for it; on a repo that is already set up, nothing changes. Any command will do, here `lore sync status`. The hooks are in `.git/hooks`, and the driver is in the clone's own git config:

<!-- example: sync#hooks only=1,2,3 -->
```console
# alice, in website
$ lore sync status >/dev/null
$ ls .git/hooks | grep -v sample
commit-msg
post-checkout
post-commit
post-merge
post-rewrite
pre-commit
pre-push
$ git config --get-regexp '^merge\.lore' | sed "s|'/[^']*'|/path/to/lore|"
merge.lore.name lore field-level row merge
merge.lore.driver lore merge-driver %O %A %B %P
merge.lore-keep-ours.name lore: keep ours, re-render after merge
merge.lore-keep-ours.driver lore merge-driver --keep-ours %O %A %B %P
```
<!-- /example -->

<!-- ds:block id=sync-mergedriver-config-cthptudb -->
There are two drivers. When the lore that sets them up is the `lore` on your PATH, they call plain `lore`, as above, so they keep working when a package manager moves the binary on an upgrade. When it is another binary (a build outside PATH, a second copy), they name that binary by its full path (`'/path/to/lore' merge-driver …`), so a merge uses the lore that wrote the notes. Once a working driver is set, lore leaves it alone: running some other lore binary in the clone never repoints it. lore rewrites a driver only when it is missing, or when it names a full path that no longer exists (a deleted build); `lore init` and `lore doctor --fix` also replace a value that is not lore's driver at all, which `lore doctor` reports. `lore` merges row files field by field. `lore-keep-ours` is for the files render generates at a fixed place (`.lore/LORE.md`, `.lore/LORE.full.md` and the path rule files `.claude/rules/lore/lore-*.md` and `.cursor/rules/lore-*.mdc`): on a merge it keeps your side, and the next lore command writes the file again from the merged notes. If one of them is still left unmerged (a merge without the driver, or a `.gitattributes` from before a rule existed), `lore doctor` counts it under `open conflicts` and names the fix: `lore render && git add <file>`.

<!-- ds:block id=sync-gitattributes-symdu732 -->
The `.gitattributes` lines (shown in [How notes travel with git](how-notes-travel-with-git.md#step-1--set-up-lore-and-commit-what-it-wrote)) tell git which files use which driver. They also force plain `LF` line endings (the invisible end-of-line character) for note files, so Windows and macOS machines write the same bytes, and mark the files as generated, so GitHub folds them in pull request diffs.

## Step 2 — Read a hook

Each hook gets one block between `>>> lore-sync >>>` and `<<< lore-sync <<<` markers. A hook calls the first `lore` on your PATH, whichever lore build wrote it: a second build run as `lore-dev`, a copy outside PATH or a build run with its own `LORE_HOME` writes the same bare blocks. To have a clone's hooks run another build, ask for it there: `lore fix --pin-hooks` (or `lore doctor --fix --pin-hooks`, `lore sync --pin-hooks`) run with that build makes the first line of each block name it (ending `# lore-pin: …`) and run it with its `LORE_HOME`; only when that file is gone does the block fall back to the first `lore` on PATH. Setting `LORE_HOOK_BIN` to a wrapper script's absolute path pins the wrapper the same way, unless the wrapper sits in a `tmp` folder or a lore source tree or `LORE_HOME` is not the default (those take `--pin-hooks`). A later command of another build keeps a pin you asked for; the `lore` on your PATH removes every pin the next time it writes the hooks (`lore fix`) and says `hooks: removed the pin to <path>; they run lore from PATH`, and any build removes a pin an older lore wrote by itself (ending `# lore-bin: …`). The pin is only written into the clone's own `.git/hooks`, which is never committed; a hooks folder in the work tree (husky's `.husky`, a committed `.githooks`) or one every repo shares (`core.hooksPath` in your global git config) always calls the first `lore` on PATH. `lore doctor` warns while the blocks are pinned, naming the build, its `LORE_HOME` (and whether it is gone) and the command that removes the pin (`lore fix` run by the lore on PATH); run by another build, it notes that the blocks run the lore on PATH and that `doctor --fix --pin-hooks` run with that build pins them to it. The block does nothing when lore is not installed, and it checks that the installed lore knows the command before it calls it. A commit that changes nothing under `.lore/data` (a code-only commit) starts no lore at all in pre-commit: one `git status` of that folder decides, and commit-msg adds the `Lore-Task:` line and runs the leak check in a single lore call (falling back to the separate calls, as before, with a lore that cannot do both), so a code-only commit pays one lore start-up there instead of six. One case is refused on purpose: when a commit changes `.lore/data`, which holds lore 0.1.18 row files (`"_v": 2`), and the lore the hook runs is older, the pre-commit hook stops the commit and names two ways out (run `doctor --fix --pin-hooks` with your 0.1.18 build so the hooks run it, or install lore 0.1.18 or newer as `lore`), because an older lore cannot check the new files:

<!-- example: sync#hooks only=4 -->
```console
# alice, in website
$ cat .git/hooks/pre-commit
#!/bin/sh
# >>> lore-sync >>>
( { d="$(git status --porcelain --untracked-files=all -- .lore/data 2>/dev/null)" && [ -z "$d" ] && exit 0; true; } && if command -v lore >/dev/null 2>&1; then if ! lore migrate --help >/dev/null 2>&1 && grep -rqsE '"_v": *2' .lore/data; then echo "lore: .lore/data holds lore 0.1.18 rows but the lore these hooks run ($(command -v lore)) is older; run doctor --fix --pin-hooks here with your lore 0.1.18 or newer build (e.g. lore-dev doctor --fix --pin-hooks) so the hooks run that build, or install lore 0.1.18 or newer as lore" >&2; exit 1; elif lore sync hook --help >/dev/null 2>&1; then lore sync hook pre-commit; else echo "lore: installed lore cannot check .lore/data (no 'sync hook'); upgrade it" >&2; fi; fi ) || exit $?
# <<< lore-sync <<<
```
<!-- /example -->

| Hook | What lore's block does |
|---|---|
| `pre-commit` | refuses the commit if a changed note file is broken JSON or has conflict markers, or if the lore the hooks run (the build that set them up, else the first `lore` on `PATH`) is older than 0.1.18 while `.lore/data` holds 0.1.18 rows (a commit that changes no row file has nothing for this hook and goes through); refuses a commit that deletes a row file you removed by hand (`rm .lore/data/rules/<id>.json`: lore itself never deletes a row file, a `lore <noun> delete` keeps it in the trash with an audit entry), naming each row (`must rule "tests green before push" rul_…`) with `git checkout HEAD -- <file>` to bring it back and the `lore <noun> delete --id <id> --yes` to run once it is back to delete it on purpose, or `LORE_ALLOW_ROW_DROP=1 git commit` to commit the deletion as it is (`lore doctor` names such rows too); a row file you renamed (its id still in the commit) is no deletion; otherwise stages the row files lore wrote in `.lore/data` and names them in one line (`lore: added 2 lore row file(s) to this commit: …`, up to five; nothing when it added none); when nothing else is staged it adds none and says so (`lore: 1 lore row file(s) left out of this commit: …`), because git decides whether a commit has anything in it before its hooks run, so a plain `git commit` or `git commit -a` would stop at `nothing added to commit` anyway: commit them with `git add .lore/data && git commit`; it never stages the files a `lore fix` format migration rewrote and you have not committed yet (it says how many it left out: commit them on their own with `git add .lore/data && git commit`); when the commit carries row files and `.lore/LORE.md` is committed, it renders it again from those rows and stages it with one line (`lore: refreshed .lore/LORE.md in this commit for the row files it carries`), together with `.lore/LORE.full.md`: when that is committed, or when this render wrote it for the first time (a project made by lore 0.1.17 never had one, so the commit `lore migrate run` prints adds it and the line ends `(and added .lore/LORE.full.md beside it)`); a full file git ignores, one lore did not write, one that was already on disk untracked before the commit (you left it out, or ran `git rm --cached .lore/LORE.full.md`), and any new full file in a client repo stay out of the commit; so a checkout of the commit has nothing to re-render and `git status` is clean after it; whenever a commit hook refuses, your index is put back exactly as you staged it |
| `post-checkout`, `post-merge`, `post-rewrite` | reads the new files in at once after a checkout, pull, merge or rebase; never fails the git command, and changes no file while a rebase, merge, cherry-pick, revert or bisect is still running (so `git pull --rebase` never stops on `.lore/LORE.md`): it renders when the rebase ends, or the next lore command does. A committed `.lore/LORE.md` that you have not changed is left as it is after every checkout, pull, merge and rebase, so no tracked file turns dirty in the middle of your git flow (the next `git pull --rebase` or `git merge` never stops on it, and discarding the file sticks). After a merge or a rebase that combined rows from two sides it can lag behind the rows until the next commit that carries row files, whose `pre-commit` hook renders it again, or until you run `lore render`. `lore sync` keeps the same rule: on a clean tree it leaves a committed `.lore/LORE.md` as it is even when it brought rows in (a store's, a teammate's live writes), so the next `git pull` (merge, `--rebase` or `--ff-only`) never stops on it; it refreshes the file only when your own row files already hold changes you have not committed. When it leaves the file behind its rows it says so in one line (`lore sync: .lore/LORE.md is behind its rows (rows that reached this clone since it was committed); it stays as committed so your next git pull works. It catches up with your next commit that carries row files, or run lore render and commit it.`). While a rebase, merge, cherry-pick, revert or bisect is stopped in the work tree (on a conflict, say), `lore sync` and `lore render` leave the tracked render and pointer files as they are too, so `git rebase --continue` and `git merge --abort` work as git means them; each says so in one line naming the operation and what to run after it (`lore sync: a git rebase is in progress in this clone, so .lore/LORE.md and the other tracked files lore renders stay as they are (a changed tracked file would stop it); finish it with git rebase --continue (or git rebase --abort), then run lore render and commit the result.`; `lore render` prints the same after `lore render: nothing written:`). When the render changes `.lore/LORE.md` or `.lore/LORE.full.md` it says so in one line (`lore: re-rendered .lore/LORE.md for the rows git brought in; commit it with your next change`); a render with the same bytes says nothing |
| `commit-msg` | when the lore the hooks run is older than 0.1.18 while `.lore/data` holds 0.1.18 rows, that lore cannot check the commit: a commit that carries row files, or any commit in a client repo, is refused naming that lore and the fix (`doctor --fix --pin-hooks` run with a 0.1.18 or newer build), and any other commit (a README change) goes through; otherwise it adds a `Lore-Task:` line for the task you are working on, then checks the message and staged text files for secrets (a binary file, one with a NUL byte in its first 8000 bytes as git decides, is skipped, as gitleaks does) and for internal notes that must not reach a client repo (see [Lore for teams](../team/README.md)); only what the commit adds is refused: a secret-looking value the same row (or the same file) already held in the history you pushed (the last commit when nothing was ever pushed; a commit the remote holds only behind a pushed tag counts as pushed, and so does a value the remote's branch already holds at the same path, as after a squash merge of your branch), as after a `lore fix` format rewrite or a moved row file, lets the commit through with one line that counts the rows (`lore check leaks --rows` lists them) and, for any other file, one line naming each file and line and the ref that already holds the value (`origin/main`, `tag v1.2`, or HEAD when no remote has it); a value in a commit you have not pushed yet (one made with `--no-verify`) is still new, so `git commit --amend` checks every file of the commit it replaces and is refused until the value is gone; a secret in the commit message itself gets a `fix:` line (edit the message, or `git commit --amend`), never an allow command; in a client repo it refuses the commit when no lore on `PATH` can do that check; when the lore the hooks run is older than 0.1.18 while `.lore/data` holds 0.1.18 rows, a commit that carries no row file (a README change) goes through, and a commit that carries one, or any commit in a client repo, is refused with the same line as `pre-commit`, naming that binary and `doctor --fix --pin-hooks` |
| `pre-push` | checks every file version and commit message the push sends that the remote does not have for secrets (in a client repo also for internal ids and internal sentences, and refuses the push when the store cannot be read); as at commit, a secret-looking value the same row already held in a commit the remote has (through a branch or a pushed tag) is not new, and a file version the remote holds behind a pushed tag is not sent again; the internal-text check reads only the lines the pushed commits add, without the lines the same file already holds on that remote (the ref a force-push replaces, its other branches, its tags) and the commit messages it already holds, so a rebase and force-push is not refused for text already on the remote; so a commit that passed the commit check (a `lore migrate run` rewrite) also pushes, with one line that counts the rows and one that names each other file, line and the remote ref that already holds it; a push of several commits that change one file checks every version of it, not only the newest (a key a `git commit --no-verify` put into a row file is refused even when an earlier commit of the same push changed that file too); each refused finding prints its ready `lore secrets allow --row-id <row-id> --field <field> --rule <rule> --match-hash <sha256:…>` line: run it, commit the new `.lore/data/secret_allows` file and push again. `git push --no-verify` skips it |
| `post-commit`, `pre-push` | carry finished live rows (tasks on the live list that are done) to a protected main (a main branch GitHub will not let you push to directly) in a small extra commit (see [How it works › Protected main](../team/how-it-works.md#protected-main-the-ride-along-commit)); and keep the notes a `git revert` deletes: a note's file that rode in a code commit goes when you revert that commit, though you never deleted the note, so after a revert `post-commit` puts each such file back in your work tree and names it (it says the revert deleted a row you never deleted with lore and that the file is back in your work tree, so the note stays; then the `git add … && git commit -m "lore: keep rows a revert removed"` that commits it and the `lore <noun> delete --id <id> --yes` that drops it on purpose), and `pre-push` refuses a push that carries a revert deleting a row the pushed tip still lacks (`E_NEEDS_CONFIRM`, naming each row, the `git checkout <revert>^ -- <file>` that brings it back, and `LORE_ALLOW_ROW_DROP=1 git push` to drop it anyway); a revert of several commits (`git revert A..B`) is caught at the push, and a revert of a commit that holds only lore's files (a note you committed on its own, a format migration) deletes them as you asked |

## Try it — a broken note file is refused

Alice breaks a note file by hand and tries to commit it. The pre-commit hook stops the commit and names the file; restoring the file fixes it:

<!-- example: sync#commit-refused -->
```console
# alice, in website
$ printf '{ broken' > .lore/data/rules/rul_b4f4…a5b0.json && git add .lore
$ git commit -m 'oops'
ERROR: [E_INVALID_INPUT] refusing to commit broken lore files:
  .lore/data/rules/rul_b4f4…a5b0.json (invalid JSON)
  hint: fix the file by hand (a row file is one JSON object named after its own id; settle a conflict with the row's edit command), or restore it with `git checkout HEAD -- <path>`; then commit again
(exit 1)
$ git checkout -q HEAD -- .lore/data && git status --short
```
<!-- /example -->

The hook names each refused file on its own line with the reason: invalid JSON, conflict markers (an unresolved git merge: `lore sync conflicts` lists it), a row whose id is not its file name (and, when the file named after that id exists too, `holds that id too (a duplicate id)`), including a case-only rename such as `MEM_….json` for `mem_….json` that a case-insensitive checkout or a Windows tool makes (the refusal gives the `git mv` back to the lowercase id; until then every read names the file instead of leaving the row out silently), a file it cannot read (`permission denied` with the `chmod u+rw <file>` that fixes it), or a deleted `.lore/data/_meta.json` (the project's id and format; `git checkout HEAD -- .lore/data/_meta.json` puts it back). A commit that deletes the whole `.lore` folder is refused with `refusing to commit the deletion of the lore project folder .lore` and the `git checkout HEAD -- .lore` that puts it back; to take lore out of a repo on purpose, commit with `git commit --no-verify`. A row file an editor saved with a UTF-8 byte order mark (Windows Notepad) is not refused: the hook removes the mark, says `lore: removed the UTF-8 byte order mark from <file>`, and commits the file as plain UTF-8.

## Rewriting history: rebase, amend, force-push

A note lives in a commit, so a rewrite of history can take notes away with no delete anywhere. lore's hooks watch for it:

- **A push that may be refused sends no live writes.** Your `git push` to the live remote sends the waiting live writes only when the branch push is a fast-forward as far as this clone can tell: the remote's commit is known here and an ancestor of what you push. When a teammate pushed first and you have not fetched, git refuses the push (`fetch first`); lore then keeps `refs/lore/live` too and says once `lore: live rows not sent with this push (the remote has commits you do not have); they go with your next lore sync`. A forced push waits the same way (a forced push that replaces the remote's commits). When git refuses the branch as non-fast-forward after a fetch, the line names it (`lore: live rows not sent with this push (main and origin/main have diverged: git refuses it as non-fast-forward); …`). The rows go with your next `lore sync`, or your next push that goes through (after `git pull --rebase`). A push with nothing new on the branch still sends them.
- **A forced push that takes notes off the remote is refused.** The pre-push hook compares the remote branch (as this clone fetched it) with what you push. When the push is not a fast-forward and row files on the remote would be gone with no commit deleting them, it stops with `E_NEEDS_CONFIRM` and lists them (`dec_… (decisions, in 3aabf17 "Record Go pin decision")`). Keep them: `git pull --rebase` and push again. Drop them on purpose: `LORE_ALLOW_ROW_DROP=1 git push --force-with-lease`. A remote tip this clone never fetched cannot be compared: fetch first (`--force-with-lease` refuses that push anyway).
- **A rebase that leaves notes out says so.** After `git pull --rebase` drops your own commit as already upstream (someone force-pushed over it), or any rebase leaves row files out that no commit deleted, the hook prints `lore: this rebase removed 1 lore row that no commit deleted` with each id and `bring back: git cherry-pick <commit>`.
- **Commit links follow a rebase or an amend.** The post-rewrite hook gets git's list of old and new commit ids and moves each [commit link](../tasks/link-commits.md) to the new commit (`lore: moved 1 commit link(s) to the rewritten commits`). After a rebase lore commits the link files it changed in one small commit of its own on top of the rebased branch (`chore(lore): move 1 commit link(s) to the rebased commits`; files you had already changed stay out of it), so the rebase ends with a clean tree and the next `git checkout` works; after an amend, commit the changed `.lore/data` with your next change. A rewrite made without lore's hooks leaves links on the old commits: `lore doctor` names them (`commit_links: … on no branch`) and `lore link remap --pair <old>=<new>` moves one. A rewrite that also drops the old commits (`git filter-repo`, BFG) is found from the map the tool leaves in the clone: doctor says `commit_links: … name a commit that no longer exists in this repository` with the ready `lore link remap --pair <old>=<new>` when the commit has a new id, and `lore commit show --id <old>` adds a note that the commit does not exist here.
- **A missing id names the commit that has it.** `lore <kind> show --id <id>` for a row whose commit is on no branch any more, but still in this clone's reflog, answers with `git cherry-pick <commit>`.

lore's own backups are local refs, never pushed (`lore where` lists them): `refs/lore-backup/migrate/<date>` is the state before `lore migrate run` (put it back with `lore migrate rollback`), `refs/lore-backup/live/<stamp>` is your live ref before a live compaction or a rewritten remote live ref (put it back with `lore live restore`), and `refs/lore/backup/epoch-<n>-<sha>` in a store clone is that clone's history before it adopted a compacted store. None of them covers a force-push of your branch: there git's reflog is the backup (`git reflog`, then `git cherry-pick <commit>`).

## Pitfalls

- **lore never changes `core.hooksPath`** (the git setting that says which folder holds the hooks), except when you opt in with `lore setup guard install`, which points your global `core.hooksPath` at lore's dispatchers in `~/.lore/git-hooks/` so client repos lore never ran in are guarded too; each dispatcher runs the repo's own hook (or your earlier global folder's) first, lore keeps writing its blocks there, and `lore setup guard remove` restores the setting exactly ([client repos](../team/client-folders.md#step-5--a-client-repo-that-holds-no-lore-files)). When a hook manager owns the hooks folder, lore adds its block to the scripts there. Its block goes right after the first line, so an early `exit 0` in your own script cannot skip it.
- **A global `core.hooksPath` folder runs lore only where lore is set up.** When `core.hooksPath` comes from your global or system git config, that one folder holds the hooks of every repo on the machine. lore still adds its blocks there (the `set up git` line says the folder is shared), but each line starts with a check: it runs lore only when the repo has a `.lore/` folder or lore wired that clone (`.git/lore/git-wiring`). In any other repo the blocks do nothing: a commit there starts no lore, adds no git config key, fetches no `refs/lore` and writes no file.
- **A commit fetches no more than any lore command.** The hook blocks read the org stores' links within `live.fetch_ttl` (5 minutes), like every command; only `lore sync` itself fetches every org store each time. An everyday `git commit` therefore makes no network call when lore fetched in the last 5 minutes, and a teammate's link made a minute ago reaches your commit's checks after your next `lore sync`.
- **Upgrading from v0.1.17: update every `lore` on your PATH.** After `lore migrate run` the row files are in the 0.1.18 format. If an old v0.1.17 `lore` is still first on your PATH (an old Homebrew or `~/.local/bin` copy, or a second machine), every `git commit` in that repo that changes `.lore/data` is refused with `lore: .lore/data holds lore 0.1.18 rows but the lore these hooks run (…) is older` when the hook block calls the `lore` on PATH (one written by the build that is that `lore`, or one whose pinned build is gone). A clone where lore 0.1.17 itself ran before the migration keeps 0.1.17's own hook until this lore runs there, and that hook refuses every commit (code too) with one `newer-format … upgrade lore` line per row and `refusing to commit broken lore files`, ending in an unrelated hint about removing a credential; `git commit --no-verify` gets past it until the lore on PATH is upgraded. Run `which lore` and `lore version` and upgrade or remove the old copy; the merge driver calls the same `lore` on PATH (or the full path it was set up with), so upgrade that one too.
- **A committed hook that is not executable stays as committed.** git commits a file's exec bit with it. When a committed hooks folder (`.githooks`) holds lore's blocks in files committed without that bit, a sync, a write or `lore doctor --fix` leaves them exactly as they are (bytes and mode), so a teammate's `git status` stays clean; git does not run such a hook, so `lore doctor` names it, and `lore fix --tracked-hooks` makes it executable for you to commit.
- **A fresh clone has no hooks until lore runs.** git does not copy hooks when you clone. Run `lore sync` once; until then, a merge in that clone uses plain line merging.
- **`LORE_SYNC_GIT=0` leaves git alone.** With it set, lore still syncs files but never adds hooks, the driver or lore's merge rules (in `.gitattributes` or `.git/info/attributes`). Use it on build machines where you do not want lore to change the clone.
- **The hint after a refused commit talks about markers even for broken JSON.** If the message says "invalid JSON", the file is not valid JSON at all: restore it from git (`git checkout HEAD -- <file>`) or fix the text.
- **Removing lore's block by hand is undone in your clone.** lore checks the set-up after every command and puts a removed hook block back. A block removed from the committed `.gitattributes` comes back in the clone's own `.git/info/attributes` (a plain lore command changes no tracked file outside `.lore/`), and `lore fix` or `lore doctor --fix` writes it to `.gitattributes` again for you to commit. To stop it, set `LORE_SYNC_GIT=0`.
- **Missing blocks turn the leak guard off, and lore says so.** When the `commit-msg`, `pre-push` or `pre-commit` block is gone from a clone lore set up before (removed by hand, or a hook manager took the hooks over with `core.hooksPath` or its own `pre-commit` script), `lore doctor` lists first `leak guard off in this clone: lore's hook blocks are missing in <folder> (…), so commits are not checked for secrets …; run `lore fix` to restore them`, and the next lore command says it once as well. That one line is the whole diagnosis: doctor adds no second line about the same blocks (a missing `post-commit` block, which is no guard hook, is named at the end of it: `the post-commit hook block is missing too, so rows cannot ride along on a protected main`), and when `core.hooksPath` points at a hook manager's folder it adds that `lore fix` must run again after the manager reinstalls its hooks (a reinstall rewrites the folder without lore's blocks). Both also scan the commits no remote has yet, as the pre-push check would, and name a secret-looking value in them with its `lore secrets allow` line: rewrite that commit (`git commit --amend`, or `git rebase --interactive`) before you push.
