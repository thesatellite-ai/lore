# Which file your coding tool reads

**In short:** `lore render` writes your most important notes into one file, `.lore/LORE.md`, and puts a short pointer to it at the top of the file each of your coding tools reads when it starts. No tool is the default, and a pointer goes only to a tool the repo already uses or one you picked for it: lore wires the tool files your repo already has (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, a Cursor rule, the Copilot instructions); in a repo that has none yet, the tools picked by the setup that applies to the folder (Claude Code gets `CLAUDE.md`), else `AGENTS.md`. Name another tool or file with `--target`; it always wins. Notes from private stores (your company's store, your personal store) go to files outside the repo, so they are never committed.

## The options in one table

| You want | Command | What it writes |
|---|---|---|
| The default | `lore render` | `.lore/LORE.md` and `.lore/LORE.full.md`, plus a pointer block in every tool file that already carries one; in a repo where none does yet, in the tool files that exist, else in `AGENTS.md` |
| A tool lore knows | `lore render --target cursor` (profiles: `claude_code`, `codex`, `cursor`, `gemini_cli`, `copilot`, `generic`) | a pointer block in that tool's file (`.cursor/rules/lore.mdc` here) |
| Any other file | `lore render --target AGENTS.md`, or a profile of your own under `context.profiles` in `~/.lore/config.yaml` | a pointer block in that file |
| Two tools at once | `lore render --target claude_code,codex` (or `--target` twice) | one pointer in each file, this render only |
| One more tool, kept | `lore render --add-target claude_code` | adds the tool to the repo's `context.targets` (keeping the ones there) and writes its file; every later plain `lore render` keeps it |
| The notes file somewhere else | `lore render --out docs/agent-notes.md` | `docs/agent-notes.md`, and the pointer names it |
| Only the notes file, no pointer | `lore render --no-pointer` | `.lore/LORE.md`; no agent file is touched |
| Only the "use lore" instructions | `lore directive install --target AGENTS.md` | the directive block at the top of `AGENTS.md`, no pointer |
| A look before writing anything | `lore render --dry-run` | nothing; prints the file instead |
| Notes from private stores (company, personal) | `lore render` (nothing extra) | one file per store under `~/.lore/render/<repo name>-<repo id>/`, named `<store name>-<store id>.md` (with an `index.md` listing them in the order of their names), outside the repo (one folder per repo: a checkout without its repo id yet uses its `prj_` project id, and the first render after the repo id arrives by `git pull` removes that folder; `lore doctor` names one still left and `lore fix` clears it), and an import of each in the tool's private file (`CLAUDE.local.md` for `claude_code`, a Cursor rule for `cursor`), hidden from git |
| To check the size in CI | `lore render --check` | nothing, not even inside `.git` (no hook, config key or `info/exclude` line); fails when `.lore/LORE.md` would be over its budget or a committed rendered file is stale (a file kept only on this machine, such as the private render under `~/.lore/render`, is never in a clone, so it is listed as a note and never fails the check); over the warn level (80% of the budget) it prints a warning and passes; a repo that never rendered passes with a note, as `lore doctor` lists it |
| A tool that cannot follow an import line | `lore context --internal` | nothing; prints the private notes for this repo as text |
| One short skill file from a folder of markdown | `lore skill compile` | a draft, `SKILL-<target>-draft.md`, for you to review |

A **pointer** is a short note that says "read that file too". It is a few lines between `<!-- lore:pointer:start -->` and `<!-- lore:pointer:end -->`. Its main line is `@.lore/LORE.md`, which tools that support imports follow; a comment under it tells other tools to read the file. Your own text outside the markers is never touched.

## If this, then that

- **If the repo already has your tool's file,** run `lore render` and commit that file and `.lore/LORE.md` with your notes. `lore init` already wired it and said which tools it found.
- **If your setup lists more tools than the repo uses** (the setup names your tools across every repo), `lore render` wires only the repo's own tools and names each skipped one with the command that adds it: `skipped codex (AGENTS.md): your setup lists it but this repo does not use it, so no AGENTS.md was written; add it with: lore render --add-target codex`. The same rule holds for `lore init`, `lore directive install` and the render `lore org link` and `lore sync` run, so linking a repo to the org store never adds another tool's file to it.
- **If you add a tool later,** run `lore render --add-target <profile>`: it saves the tool in `context.targets`, so a plain `lore render` keeps its file current. `--target` wires a file for one render only (use it for a file that is not a tool profile). lore never wires a new tool file behind your back; a plain `lore render` names the file and the command.
- **If your tool is not in the list,** add a profile for it (`name`, `pointer_file`, `import`, `budget`) under `context.profiles` in `~/.lore/config.yaml`; `lore config check` reports mistakes in it.
- **If you keep your own text in the agent file,** write it outside the pointer markers; render replaces only what is between them.
- **If a note must be seen in every session,** make it a `must` rule. Render pins (always copies into the file) only `must` rules and `critical` or `high` hotfixes. The rest is found with `lore search`, which the directive (the "use lore" instructions block) tells the tool to run.
- **If you work in a client's repo,** run `lore render` as usual. The committed `.lore/LORE.md` holds only the repo's own notes and those of stores marked `shareable`; your company's and personal notes go to `~/.lore/render/`, imported through the tool's private file.
- **If the repo is one of your org's own repos, linked with `lore org link --own` and holding no `.lore` folder,** its notes live in the store folder. `lore render` writes only the private render under `~/.lore/render/` (and the import in the tool's private file, which git ignores); it writes no `.lore/LORE.md`, so `git status` stays clean, and says so. `lore render --report`, `--dry-run` and the render itself say the same: no LORE.md and why, how a tool gets these notes, then the private part (`--report` counts its pinned rules and hotfixes). A tool gets them three ways: the private file, which Claude Code (`CLAUDE.local.md`) or Cursor (`.cursor/rules/lore-private.mdc`) imports when it is one of the repo's tools (a tool your setup lists but the repo does not use gets no private file; render says `skipped cursor (.cursor/rules/lore-private.mdc): … it is added once the tool's own file is here (.cursorrules or .cursor/rules/*.mdc)`, since such a repo keeps no `context.targets` setting); `lore context --for-file <path>` / `--for-prompt <text>`, which pick from the linked folder and the org folder (`lore context --topics` counts those same rows, so its rule count matches `lore rule list` there, and `--topic <name>` finds a tag kept in the org folder); and the agent hooks (`lore setup --agent-hooks`, once the tool's folder such as `.claude/` exists or the repo's `context.targets` names the tool), which run that context per file and prompt. The always-on rules (must rules, critical and high hotfixes) come with the private file and with the agent hooks' session start: the SessionStart hook serves them once, as the private file shows them (in full, or as its one-line index entries when the budget holds no more), in a repo with no LORE.md (a repo with a LORE.md has them there and gets nothing extra); the per-file and per-prompt context picks rows by path and words (a rule's body names a file only by its whole repo-relative path: `--for-file main.go` does not pick a rule about `saas/cmd/cron/main.go`). `lore sync` in such a repo refreshes the private file, as it does where a LORE.md is, and prints one line for each local file it wrote or removed (`wrote CLAUDE.local.md (git-excluded): imports the private context under ~/.lore-dev`). The import names the render under the lore home in use: `~/.lore/render/…` for the default home, `~/.lore-dev/render/…` under `LORE_HOME=~/.lore-dev`, an absolute path for a home outside your home folder; an import an older lore wrote with `~/.lore/render/` is replaced. `lore init` adds a `.lore` folder when you want a committed LORE.md too.
- **If the private files are bigger than you expect,** look at `lore render --report`: its private section counts the pinned rows, the rows shown and the notes left out. The setting `context.budget.internal` (32000 bytes by default, room for the pinned part of a typical 300-row folder plus the org folder's rules) is a hard limit for all the private files of the repo together, pinned rows included. Must rules and critical or high hotfixes are written in full while they fit, in rank order: critical hotfixes, then must rules for every file, then high hotfixes, then must rules for some paths, newest first within each; every other pinned row becomes one line of a "Pinned rows shown as one line" index (its id, severity, its summary, title or first sentence of at most 120 characters, and the paths it applies to when not every file). Only when even the index does not fit are the last rows left out of it, and the file then says how many and that `lore rule list` and `lore hotfix list` list them. The full text is one command away: `lore show --id <id>`, and `lore context --for-file <path>` prints every rule that applies to the file in full, the indexed ones included (that command has no cap). lore keeps everything it adds to a tool's instruction files (LORE.md and the private files together) under 40000 bytes, whatever the settings: a `context.budget.internal` above 40000 less the size of `.lore/LORE.md` is clamped, as is a LORE.md budget above 40000, and render says so (`context.budget.internal 100000 clamped to 36944: …`). `lore render` prints how many pinned rows are in full and how many are index lines (`11 pinned rules and hotfixes in full, 249 as one-line index (full text: …)`), and `lore doctor` prints the same and, when the pinned rows in full alone are over the budget, warns with the 10 longest rows. That WARN line (printed once, by the command that changes a private file: a write that refreshes it, `lore render` or `lore sync`; not on every `lore sync`, and only to someone who can fix it: an admin of the folder, or whoever may lower enough of the pinned rows) names the fixes as commands: a lower severity takes a row out of the pinned part (`lore rule edit --id <id> --severity should`, `lore hotfix edit --id <id> --severity medium`), a shorter summary or body shortens it, or, when what is pinned fits under the ceiling, `lore policy set --key context.budget.internal --value <n> --yes` raises the budget to fit, with `--to <place>` naming where the budget is set by the attached name of the store that holds it (a store's org folder `--to <org>/org`, a store attached whole by its own name such as `--to kb`, a project folder `--to <org>/<folder>`; in a repo linked to a store folder, which keeps no rows of its own, that folder), never a placeholder, so the printed command works where it is printed; when the linked folder is not attached here the raise names the link's own `--to <store>/<folder>` (the store's name in `~/.lore/config.yaml` and the link's folder), and only when no store of `config.yaml` holds the link does the line print no command and say to raise it in the store folder `lore whoami` names. A row of company ground (any folder of the company store: the org folder, a store root every folder reads, a project folder) and a budget set there are an admin's to change: an admin of the org is shown the warning with those commands; a member who can fix nothing there (the rows and the budget are all company ground) gets no warning at all, and `lore render --report` shows them the sizes with no command; a member who can fit by lowering rows of their own is shown those fixes and told which admin to ask for the rest (`ask an admin of <org> (<names>) to …`), with the admin's commands after `the admin would run`, never as the member's own next step. A rule's `trust` shows only when it differs from the default 0.50, and a body line that only points at a lore row file (`Source: <repo>/.lore/data/….json`, kept by rows imported from a repo) is left out of every rendered file and of `lore context`; the row itself keeps it.
- **If your tool has no private file** (`codex`, `gemini_cli`, `copilot`), or your CI job can read only one file, feed it the output of `lore context --internal`, and never paste that output anywhere the client can read.
- **If you want to know what the tool was given,** run `lore why-context`.

## Pitfalls

- **Never edit `.lore/LORE.md` by hand.** The next render replaces it. Change the notes and render again.
- **Render again after you add or change notes.** When a `git pull` brings in a teammate's notes, lore refreshes `.lore/LORE.md` by itself, but only at the default path and only when you run lore from the repo root. A file moved with `--out` and your own new notes wait for the next `lore render`.
- **The private file is for this machine only.** Lore hides `CLAUDE.local.md` (and the other tools' private files) through `.git/info/exclude` (a private ignore list that stays on your machine), never through the client's `.gitignore`, so the client never sees that it exists. Do not commit it.
- **Each tool has a budget.** Render prints a `must` rule in full or as one line by how much room the tool's budget leaves; `lore render --report` shows what was cut, and `lore pin set --id <id> --context full` keeps one rule in full.
- **`lore skill compile` sends your text to an outside service.** It needs network access and an account there, and every run gives slightly different output. Treat the result as a draft.
