# Adding your staff

**In short:** your own people are added straight to the org's roster with `lore member add --email <email>` (or many at once with `lore member add --from staff.csv`), with their org role, teams and projects. Nothing is pending and there is no line to send: on their laptop they run `lore setup join --invite "<the org's store url>"` (the exact command `lore member add` prints), and lore finds them on the roster by their email. Use an [invite](invites.md) only for an outsider, such as a contractor joining with a personal email.

## Before you start

- An **admin setup** for the org is active (see [Guided setup](guided-setup.md)); run with `--setup <an admin setup>` from anywhere. Without one, the member commands also run in a repo of an org whose roster gives you org role admin: `lore org create` gives its creator that role, so `lore member add` works right after it with no setup step. A member or solo setup that lore picked for the folder does not stop this; one you name with `--setup` does (`--setup personal` is refused: name an admin setup, or leave `--setup` out). The member commands run outside any repo too, and their reads (`lore member show`, `lore team show`) work in a clone with no lore project yet. From a folder no org applies to (the home folder), a member or team command with no `--setup` runs on the only org setup of this machine when there is exactly one, and says so first (`setup acme-admin (the only org setup on this machine)`); with two or more nothing is guessed. A read also names the org with `--store <org>` (`lore member list --store <org>`, `lore member show --who <who> --store <org>`), as `lore rule list --store <org>` does; without a single org setup or one of these, the hint names `--store <org>` and `--setup <setup>` with the orgs and setups of this machine.
- The teams you name exist (`lore team add --handle @web`, see [Teams](teams.md)).

## Step 1 — Add people

```sh
lore member add --email mira@agency.example --name 'Mira Dev' --handle mira --github mira-dev --role member --team @web --yes
lore member add --from staff.csv --dry-run   # who would be added
lore member add --from staff.csv --yes       # all of them, one store commit
```

| Flag | Meaning |
|---|---|
| `--name`, `--handle`, `--github` | their display name (default: the email's name part), roster @handle and GitHub login |
| `--role <r>` | an **org-level** role (`member`, `pm`, `admin`, …): no project needed; it is the role on their stint (`lore member edit --who <who> --role pm` changes it) |
| `--type <t>` | `employee` (default), `contractor`, `intern` or `client_contact` |
| `--started-on <YYYY-MM-DD>` | the first day of their stint when they began before you add them (today or earlier; default today), so a later `lore member remove` or `lore actor offboard --on <day>` can name a day before the add; one `--email` only (for people added from a file, `lore actor period edit --period <apd_id> --started-on <day>` moves the start back) |
| `--team @t` | a team to put them on (repeat it) |
| `--project <p>` with `--project-role <r>` | a project membership with its project roles (repeat both) |
| `--from <file>` | many people from a `.csv` (header `email,name,handle,github,role,type,teams,projects,project_roles`; list cells separated by `;`) or a `.json` list |
| `--from-invites` | every pending invite becomes a member, keeping its teams, projects and roles; the invite is marked accepted |
| `--dry-run` | list who would be added; write nothing |
| `--yes` | answer the confirmation without a terminal |

Every row of one run (the people, their email and GitHub contacts, stints, memberships, and each team once) is written as **one store commit** and one push, so a list of a hundred people takes seconds. A bad line (an address that is not one, a team that does not exist, an email listed twice, a line with more or fewer cells than the header) refuses the whole file before anything is written. One run lists every bad line by its line in the file (the header is line 1; a `.json` list names `entry 3`), a duplicate names both lines, and the hint is the fix for each line plus the `--dry-run` command to check the file again, e.g. `line 8: "not-an-email" is not an email address; line 9: priya@acme.test is already on line 3`. A CSV that does not parse says why and where: `line 2: a quote (") opens a cell and is never closed`. A second run adds nobody: someone who is already a member is listed as such. The last line of the output is the command each person runs, with the org's store url filled in:

```text
✓ added mira@agency.example (act_…) Mira Dev, role member, teams @web
  4 roster rows in the roster of agency (agency/org), one store commit; each person joins on their machine with: lore setup join git@github.com:agency/agency-team.git (matched by their email, no invite)
```

## Step 2 — They join

On their own machine, each person runs the command `lore member add` printed: `lore setup join --invite "<the org's store url>"`. A new member's machine has no entry for the org yet, so the org's name alone is refused there with `E_JOIN_ORG_UNKNOWN` ("no org named … on this machine yet; join with the org's store url the admin gave you"); the name works only on a machine that already has the org. lore takes the email of their identity step (their `git config user.email`), finds them on the roster, links this machine to their roster entry and sets up the org's stores. Their role, teams and projects are already there. On a terminal the command opens the setup page on the join step; without one (ssh with no tty, a script) it prints the `lore setup apply --setup <name> --step …` lines that do the same join and exits.

Someone not on the roster is refused with the reason and the command to ask for: `<email> is not a member of <org>; ask an admin to run: lore member add --email <email>`. `lore setup check --setup <setup> --step join` (and the setup page, which checks first) asks the roster the same way, so its `invite.found` check fails with that same message before anything is applied.

## Step 3 — See and change people

- `lore member list [--all]`: everyone on the roster with email, name, org role, @handle and teams (`--json`), in columns as wide as their widest cell, counted in terminal cells (a CJK name or an emoji takes two a character), and a count line (`4 members`); `lore team list` prints its teams the same way (`2 teams`).
- `lore member show --who <email|@handle|act_…>` (`--id` and `--actor` say the same; every show command takes `--id`): one person, with the names of their projects (`project_names` in `--json`). `--history` also lists their commits in the org's store clones on this machine, newest first (day and time, commit, store, subject, files), each change every reader holds back marked `[held back]`: what a person who left did, and when.
- `lore member edit --who <who> [--name] [--handle] [--role]`.
- `lore member remove --who <who> [--reason] --yes`: they leave the org (`lore actor offboard`: their stint and memberships end, they are taken off every team, the row stays for history; all of it is one store commit and one push, so a teammate never fetches half a removal). From then on their own lore refuses writes to the org's stores and repos, from any folder (a repo, or inside the store's clone; a hand edit in the clone is held, not committed) (`E_REFUSED` "you are marked as left in <org> since <day>", after their next `lore sync`); their personal store keeps working. That next `lore sync` sends nothing they wrote after the removal: a store clone of the org (also one the repo does not attach, which `lore sync` and `lore store push` send) or the repo's `refs/lore/live` holding a commit made after it is not pushed, and the sync says so once per clone (`lore: store <store>: you are marked as left in <org> since <day>: writes made after that are not sent to its stores or repos (…); 2 local commit(s) kept on this machine, not pushed`). Commits waiting in such a clone from before the removal stay on their machine with the later ones; nothing is deleted, and an admin's `lore member add` lets the next sync send them all. A clone holding only writes made before the removal is pushed as usual. When `lore store push` of such a clone sends nothing, it is refused with `E_REFUSED` and the same line. The output lists their open tasks in the stores it reads (run it in a repo to see that repo's; outside a repo it says none are listed) and prints the hand-over line `lore task reassign --from @<handle> --assign @<someone> --yes`, to run in each repo or store folder that holds their tasks (`lore actor offboard` prints the same line under the tasks they lead). The reassign also takes everyone who left off the task's watchers, so a leaver is no longer told about it; the task's history and a watcher's `lore inbox` name the people (`assignees Ann Lee → Bo Kim`), never act_ ids. After they left, `--from` and `lore task list --assignee` still take their `@handle` or email (the row stays on the roster); `--assign` takes only people who are still in the org: naming someone who left, by handle or email, is refused with who left and when (`E_STATUS_CHANGE` "Olga Berg (@olga) left acme on 2026-11-13; --assign takes only people still in the org").
- `lore member add --email <email>` for someone who left brings them back: active again, with their roster name; a stint that ended today is reopened, so a removal made by mistake is undone at once (`lore actor rejoin --actor <who> --type <t>` does the same on the same day). After their next `lore sync`, their writes go through again and their `lore doctor` shows the open stint at once. Teams and projects are not given back on their own: add `--team` / `--project` to the same command.
- `lore team member add --handle @web --members <email|@handle>` works for every member at once.

## Who may change the roster

Only an admin of the org (an open stint with org role `admin`, as `lore member list` shows it) removes a member, offboards or brings back a person (`lore member remove`, `lore actor offboard`, `lore actor rejoin`), marks someone left or archived, or changes another person's status (`lore actor status`); a member who runs one is refused with `E_REFUSED` "only an admin of the org can …" and the line to ask an admin to run, and nothing is written. A person still sets their own leave (`lore actor status --actor @me --to on_leave`).

The org's own rules and policies follow the same role rule. A must rule or a critical or high hotfix of company ground (every folder of the company store: the org folder, a store root every folder reads, and every project folder, which every repo linked to that project reads) reaches repos across the org, so only an admin of the org takes it out of what everyone is told: lowering its severity (`lore rule edit --severity should`, `lore hotfix edit --severity medium`), archiving it, deleting it or moving it to another store, whichever command does it: the one-row forms, the bulk forms (`lore rule delete --where`, `lore rule archive --where`, `lore hotfix archive --where`), the generic write-back `lore row edit` and `lore row move`, a pin that changes how every repo is shown it (`lore pin set --context full` or `line`, `lore pin unset`), and a `lore batch undo` that would take one out (undoing the batch that added it, or putting back an edit that raised it to must or critical/high). A bulk form that matches such a row is refused whole, naming the rows, and its hint prints the narrowed command a member may run instead (the same `--where` plus `--where 'severity:should,may'` for rules, `--where 'severity:low,medium'` for hotfixes). A policy of company ground (`lore policy set` or `lore policy unset` with `--to <org>/org`, `--to <org>/<project>` or `--to <store>`, or with no `--to` in a repo linked to such a folder) is an admin's change too. A member who runs one is refused with `E_REFUSED` "only an admin of the org can …", naming the admins and the line an admin runs, before any question and with nothing written. Adding a company rule, rewording one, and every should or may rule stay every member's; the repo's own rows, a personal store and the folders of another store (a client's, a solo store) are not company ground. A folder of another org's store with a roster of its own (an ops setup's store) is judged by that store's roster, wherever the command runs: only its admins take its must rules out, and the over-budget warning sends a member to that org's admins for its rows and budget (another org's admins for another org's rows, named per row). While the roster names no admin (an org from before org roles) nobody is refused, and a machine with no org roster has no roles to follow.

The store is plain git, so anyone who can push to it can commit a roster file by hand, without lore. Every teammate's lore therefore checks each commit it reads against the roster as it stood before that commit: a change to a stint (org role, type, start or end), to another person's roster entry or contacts, or to an invite not their own, made by a commit whose git author is not an admin, is held back; so is a change to who is on a project or a team (a membership row or a team's members, a person's own included) unless its author is an admin or a lead of that project, or a newcomer taking up exactly what their pending invite names (`lore project member add` by anyone else is refused up front); so is every change committed by a person after they were marked as left. A held change is not applied: lists, `lore render` and the agent's context read the row as the last accepted commit left it (or not at all when none was accepted). `lore sync` and `lore doctor` name each one: `held back in <store>: actor_periods apd_… (commit 3f2a9c1 by kim@acme.example): makes its author an admin and the author is not an admin`. An admin who agrees makes the change with lore (or reverts the commit), and the hold ends. A person's own rows (their actor entry, their agents, their contacts, their first stint when they join, and a rejoin an admin invited) are not held; that includes the agent a member's first write through a coding agent registers in the same commit as the row it writes, and that agent's later writes. Naming yourself the owner of an entry that was someone else's is a change to another person's roster entry and is held. A lore write of a row your clone holds back is refused with `E_POLICY_DENIED`, naming the hold (table, id, commit, author, reason) and the way out, instead of failing on every try with a bare `E_STALE`. While a roster has no admin yet (an org from before org roles; `lore doctor --fix` gives its first admin the role) nothing is held.

A commit that puts a new person on the roster is held with one reason for all its rows: "adds a person, <name> (<id>), to the roster [with an admin stint] and <author> is not an admin". lore refuses such a change before it is written, too: an admin setup whose person the synced roster names a member now (an admin demoted them) gets `E_REFUSED` "you are a member of <org> since <day> …; only an admin adds or invites people" from `lore member add` and `lore team invite`; after being made admin again, `lore sync` first.

Security note: the check trusts the commit's git author, which anyone with push access can set to another person's email. It stops a member's hand edit made under their own name and every lore command of a member or leaver; it is not proof against someone who forges an admin's authorship. Signed changes are a separate feature, not part of this release. Keep push access to the org's store to the people on its roster.

A person who was removed and runs the join line again is told so: `E_REFUSED` "<email> is on the roster of <org> (<org>/org) but marked as left since <day>", with the admin's `lore actor rejoin --actor @<handle> --type employee` line, instead of "not a member".

## Pending invites

Invites written before `member add` existed still work. `lore doctor` lists the org's pending invites with one hint: `lore member add --from-invites` turns them into members now (an outsider can keep the invite).

## Who wrote it

Rows are written by the person running the command. When a coding agent runs `lore member add` for its person, the rows are the person's (created_by is the person) and the agent's session is on the audit trail, as for every other roster write; an agent needs the org's `agents.may_manage_people` policy to change people.
