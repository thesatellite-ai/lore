# Changelog

All notable changes to lore are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.1.18] - Unreleased

lore 0.1.18: a new core under every command, and the first release whose source is under the Apache License 2.0. The prebuilt binaries (the archives on GitHub Releases, the Homebrew formula and the install scripts) contain this source and also proprietary components, such as the guided setup page; they are free to use, including for commercial work, under `BINARY-LICENSE.txt`, which ships in every archive beside `LICENSE-core-Apache-2.0` and `NOTICE-core`. A build from source is Apache-2.0 alone. Install with `brew install thesatellite-ai/tap/lore`, the install scripts (`install.sh`, `install.ps1`) or an archive from GitHub Releases; build from source with `go install github.com/thesatellite-ai/lore/cmd/lore@v0.1.18`. The release date is added when it is tagged.

### Added

- **`lore fix` fixes a project in one command.** It runs everything doctor can repair, in order (render, agent hooks, old store clones proved safe, the doctor checks' own repairs; with `--migrate`, first migrate a project on the lore 0.1.17 format), prints each step and the status after them, and a second run says everything is current; `--dry-run`, `--json`, and `--all` for every repo the setups know. `lore doctor --fix` runs the same steps, and `lore upgrade` ends with it (`--no-fix` skips it). It never changes a project's format by itself: in a project on the lore 0.1.17 format it refuses with the one line that names `lore migrate run`, and `lore fix --all` lists such projects with the command for each (`--all --migrate` migrates them).
- **Plain store folders.** Inside a store (a git store's clone or a `file://` folder store) a folder's rows sit right under it: `<folder>/<table>/<id>.json`, with the folder's `_meta.json` and `_purged.json` beside them and the root folder's tables at the store's top; there is no `.lore/data` inside a store any more (a code repo keeps `.lore/data`). A store folder may not be named like a table (`tasks`, `rules`, …): `E_BAD_PATH` names the reserved list. The org's `lore-org.yaml` sits in the org folder itself (`org/lore-org.yaml`, or `lore-org.yaml` at the top for `org_folder: .`), and `lore-store.yaml` names `org_folder` only in the store that holds the org folder (it is written with that folder's `lore-org.yaml`). A folder store keeps its lock and pending journal in `.lore-state/` (added to `.gitignore` when the folder is a git work tree). Lore writes a `README.md` into each store once, with its next commit there (never on a read, never over a person's own): what the folders are, how to browse and edit rows by hand, what lore checks and keeps in `.git/lore`; `lore doctor` notes a store without one (`store_readme`). A store folder still in the old layout is read and written where its rows are until it is moved.
- **Editing a store by hand.** A store clone is a working copy you may change with any text editor or with plain git, and every lore command picks the change up first. Before it reads a store, lore runs `git status` in its clone: each changed row file goes through the checks of a lore write (table schema, references, secret scan, policy) and, when valid, is stamped with your name and the time (a new HLC, `updated_by`, `updated_at`, so it wins over older changes when teammates sync), committed as you (your git identity; in a store your org's identity signs, your lore identity as author and the org identity as committer) ("hand edit: tasks tsk_…"; several rows in one folder are one commit listing each) and pushed per the store's push mode (in push mode `batch` the hand edit stays its own commit, trailer `Lore-Hand-Edit: true`, so the squash keeps its author), with a line saying what was committed where. A deleted row file is lore's delete (into the trash, `lore trash restore <id>` brings it back); a row file moved to another folder (same id) is lore's move ("hand move: …"); a new file named after its id is created. A file lore cannot accept is refused with `file:line` and the exact reason and stays as you left it, never committed or pushed until fixed, while your other edits go; a sync sets it aside for its merge and puts it back, so it is never overwritten and never stops the sync. Each store clone is set up for plain git: `merge.lore.driver` in `.git/config` and `*.json merge=lore` in `.git/info/attributes` (field merge on `git pull`), and a block in `.git/hooks/pre-commit` that checks the staged rows and scans for secrets before a hand commit (your own hook lines are kept; a repo-local `core.hooksPath` is set only when a global one would skip `.git/hooks`); lore's own commits skip that hook and driver. `lore doctor` names files in a store clone that are not rows (never deleted) and row files changed by hand and not committed (`store_files`). In a code repo, a hand edit of a committed row in `.lore/data` is checked and re-stamped the same way and left for your commit. Guide: docs/sync/editing-by-hand.md.
- **Stores of an earlier 0.1.18 build move by themselves.** The first command of this lore on a machine that ran an earlier 0.1.18 build moves each old store clone (`~/.lore/clones/<host>/<owner>/<repo>.git` with its `work` worktree) to a plain clone at `~/.lore/stores/<owner>/<repo>`, without the network: unpushed commits are carried (and pushed at once when the store pushes now and the remote answers), uncommitted changes are copied, an ssh-alias origin lands at the url's path and keeps its spelling (`~/.ssh/config` tells which host an alias is). Each store still in the old tree layout gets one commit `lore: store layout 0.1.18 — rows move from <folder>/.lore/data/ to <folder>/` (rows, `_meta.json`, `_purged.json`, `org/lore-org.yaml`, `org_folder` fixed, `README.md`, `lore_store: 3`), pushed per the store's push mode. Every step prints what it moved; the layout commit's line names what that commit changed and never prints a zero count (`lore: store lore-x: layout commit abc1234 — 12 rows moved to _store/, README refreshed, marker lore_store: 4`, or `— README refreshed, marker lore_store: 4` when no rows moved; a folder store prints `lore: store <name>: layout change — …`); a second run is silent; a run cut short is finished by the next. The old folders stay: `lore doctor` (`old_clones`) names each with the exact `rm -rf` command once its content is safely in the new clone, and names `~/.lore/clones-v017`, which this lore no longer uses. `lore-store.yaml` `lore_store: 3` declares the plain layout, so an older 0.1.18 build refuses such a store (`E_OLD_LORE`) instead of writing rows into the old place. Guide: docs/operations/upgrade.md.
- **Store clones are plain git clones.** Each git store has one clone on this machine, a normal git clone at `~/.lore/stores/<owner>/<repo>` (the host is never in the path; a store pinned to a branch is its own clone at `<repo>@<branch>`; a second store with the same path on another host gets `<repo>~2`, recorded in `~/.lore/state/store-clones.json`). Lore's lock, pending audit journal and fetch and push stamps live in its `.git/lore/`, never among the store's files; the branch tracks `origin`, so a plain `git pull` works there. Every writer of a store (row writes, folder add/remove, adopt, `org link`/`unlink`, the org file) takes that one lock, and the org-link code uses the same clone (no second copy under `~/.lore/clones-v017`). `lore store open` prints the store's own clone instead of making a detached worktree under `~/.lore/worktrees`. Inside a store's clone (`lore-store.yaml` at its top) lore never acts as in a code repo: `cd <store>/<folder> && lore task list` works on that folder, nothing is wired or written into the clone, and a command that needs a code repo says so.
- **`lore edit --id <id>` and `lore path <id>`.** `lore edit` opens any row (in a store or a code repo) in `$VISUAL`, `$EDITOR` or `vi` as Markdown: every field as YAML frontmatter, the row's long text as the body; saving writes it back through the normal write path (fields, references, secret scan, policy), and a refused edit names the file and line and keeps your text. `lore path` (alias `lore open`) prints the row's file, `--json` adds table, store and folder; `lore row markdown` and `lore row edit --file` do the same without an editor. Row files stay JSON.
- **`lore where` (alias `lore files`) and `~/.lore/README.md`.** One line for every file, folder, git config entry and ref lore keeps on this machine and in the current repo, with what it is and what happens if you edit or delete it (`--json`, `--all`); the README in lore's home maps the same layout in plain words, and names each cache file's store and repo.
- **Reads change nothing and every push is named.** A read never pushes, never installs hooks, merge drivers, attributes or a clone identity, and never writes into the repo (when commits wait it says `run lore sync`); every write names the row files it wrote, and every push prints `lore: pushed store <store>: commit <sha> to branch <branch>`.
- **The repo cache lives in lore's home.** A code repo's cache is `~/.lore/cache/repo/<repo folder>-<hash>.db`, never in the work tree, so a read leaves the repo, `.git/info/exclude` and `.git/config` as they were; an old `.lore/lore-cache.db` is noted by `lore doctor` (`old_repo_cache`) and removed by `lore fix`.
- **Every org store has a short name.** The repo name of its url without `.git` (`git@github.com:agency/lore-x.git` is `lore-x`), or `stores[].name` in lore-org.yaml. `lore store list` shows the org's other stores by it in the NAME column (the url in its own column), output names the store by it, and every store argument and `--to <store>/<folder>` target takes it (the url still works). Two stores of one org with the same short name are refused when the org config is read, naming both urls and "set stores[].name in lore-org.yaml".
- **Canonical store urls in shared config, each machine's own access in its config.** lore-org.yaml and `.lore/stores.yaml` name stores the way every teammate reaches them (`git@github.com:org/repo.git`); `access:` in `~/.lore/config.yaml` maps a canonical owner prefix to this machine's spelling (`url: git@github.com:org/`, `via: git@work-gh:org/`), applied to each git call as `git -c url.<via>.insteadOf=<url>`, never written into git config. `lore org create`, `org import`, `store init` and `store add` given an ssh-alias url read `~/.ssh/config`, store the canonical url, record the access rule and say so. `lore doctor` (new check `store_access`) warns about a shared url spelled with your alias and about a store this machine cannot reach, with the exact `access:` lines and the `git config --global url."…".insteadOf "…"` command; it never rewrites shared config. Every rule lore suggests or records is scoped to the owner/org path (`git@github.com:org/` → `git@work-gh:org/`, `https://github.com/org/`), never the whole host: a host-wide rule sent every github.com repo through the alias's account and broke the push of a personal store on another account. A host-wide rule already in config.yaml gets a `store_access` warning naming the stores under another owner and the owner-scoped lines; `lore doctor --fix` replaces it. A clone, fetch or push that fails through an access rule names the rule (`url → via`, from `~/.lore/config.yaml`) and the next step.
- New op `store.use` (`lore store use <path> [--store <store>]`, `POST /v1/stores/use`): use your own git clone of a store, made anywhere with `git clone`; lore checks its origin against the configured stores and that it is a lore store, refuses while lore's own clone holds unpushed work, and records the path on this machine only. `lore store use --default <store>` goes back to lore's own clone and leaves yours as it is; `lore store forget` never deletes a clone of your own.
- New ops `member.add`, `member.list`, `member.show`, `member.edit`, `member.remove` (`lore member add <email> [--name --handle --github --role --type --team @x --project <p> --project-role <r>]`, `--from <file.csv|json>`, `--from-invites`): an admin adds the org's own staff straight to the roster, no invite. Role (org-level, no project needed), teams and projects apply at once; a file of people is one store commit; a pending invite of the same email becomes the member (its teams and projects kept). The person joins with `lore setup join <org>` (or the store url), matched by their email; someone not on the roster is refused naming `lore member add <email>`. `lore team invite` is now for outsiders; `lore doctor` lists pending invites with `lore member add --from-invites`. Guide: docs/team/members.md.
- `lore team invite <email> --team @web` (repeatable): the invite carries team membership and joining adds the person to each team (a team removed since is skipped). `lore team member add @web <email>` for someone with a pending invite records the team on the invite and says so, instead of refusing them as not on the roster; `team list` counts pending members and `team show` lists them apart, with their invite.
- `lore task edit <id> --clear-tasklist` takes a task off its list (beside `--clear-mission`, `--clear-plan`, `--clear-assignee`); `task edit` with nothing to change names the `--clear-*` flags.
- `lore doctor` check `empty_ref`: rows whose ref field holds the empty string lore 0.1.17 wrote for "none" (`tasklist_id: ""`), counted per store and field; `lore doctor --fix` writes null in them, one store commit per store. In a client repo linked to a store folder by its remote, `lore doctor` now runs the store checks for that folder.
- New op `actor.merge` (`lore actor merge <from> <into> [--dry-run]`, `POST /v1/actors/merge`): one person with two actor ids becomes one. Every row naming `<from>` in the stores the command writes is edited to name `<into>` (an ordinary edit: new HLC, the audit trail kept); `<from>` keeps its row, marked `merged_into <into>` and inactive (actors are never deleted). It asks first (`--yes`), refuses merging a person into an agent, an unknown id or an actor already merged elsewhere, and a second run changes nothing. `lore doctor` warns (`actor_stable_key`) when two actors share one stable key, naming both ids and the merge command, and notes an actor keyed by a git login (no email) that is a roster person's handle as a likely duplicate, never merged on its own.
- New ops `team.add`, `team.list`, `team.show`, `team.remove`, `team.member.add` and `team.member.remove` (`lore team add @web --name "Web" --members @mira,@tomas`, `lore team list|show|remove`, `lore team member add|remove @web <people>`; REST `/v1/team/...`; `--json`): the org's teams on the org roster, so `@web` on a task (`task add --assign @web`) names the group. They run outside any repo too (the setup's org store), and a coding agent runs them as its person. `team add` on an existing team renames it or (with `--members`) replaces its members, a person's handle or someone who left is refused, and `team remove` keeps the row (tasks that named the team still read it; `team add` brings it back). Guide: docs/team/teams.md.
- New op `store.adopt` (`lore store adopt <store>/<folder> [--from <repo>]`, `POST /v1/stores/adopt`): moves a whole repo's lore data into a store folder in one pass — every row file of `.lore/data`, the rows only on a v0.1.17 `refs/lore/live`, and rows only in a v0.1.17 `.lore/lore.db` — keeping every id, HLC and relation (`project_id` becomes the folder's project), as one store commit and one push; 5,000 rows take seconds. It asks first (`--yes`), `--dry-run` counts per table, a second run writes nothing, a row the folder holds newer or deleted is kept, and the repo is never changed unless `--remove-source` (which deletes the adopted row files as an ordinary diff you commit). Works outside a repo like the other store commands. Guide: docs/team/client-folders.md, Step 7.
- New op `store.folder.remove` (`lore store folder remove <store> <folder>`, `POST /v1/store/folders/remove`): removes an empty folder (no rows, no repo links) after asking (`--yes` without a terminal), as one store commit pushed per the store's push mode, so its name is free again in another store of the org. A folder with rows or repo links is refused with the counts and the next steps (`lore move`, `lore org unlink`); `--purge --confirm` moves its live rows into the store's trash first (one `bat_`, restorable with `lore trash restore` once the folder is made again), drops its links and id. The org folder is never removed; for an org store only the org's admin may, for any other store whoever can push; `agents.person_only` applies. `lore store folder list` stops showing a removed folder, and `lore doctor` warns (`removed_store_folder`) in a repo whose `.lore/stores.yaml` still attaches it. Guide: docs/team/client-folders.md.
- `lore org link <org> --project <folder>` links a client repo that holds no lore data (no `lore init`): the link is made for the repo's remote (`--remote` picks one) with a project id derived from it and kept only in the store. Every later command in that repo resolves the link from the store by the remote, writes to the linked folder, keeps its cache under `~/.lore`, and writes nothing into the repo (no `.lore/`, `.gitignore`, `.gitattributes` or hooks); `lore doctor` there says so.
- Store commands that need only the setup work outside any git repo (from the plain parent folder of an org's client folders): `lore store folder add team <folder>` (also with the org's name or the org store's url), `lore store list` (the setup's org and personal stores), `lore store visibility|set|compact`. A `.lore/stores.yaml` name outside a repo is refused naming that cause and the names that work there; `lore store init|add|remove|set-url` and `lore org link|unlink|set|use` outside a repo say they need one instead of blaming a client repo, a missing remote or a project id.
- New op `store.folder.list` (`lore store folder list [store]`, `GET /v1/store/folders`): each folder of a store (every store the setup sees by default) with its id, who created it and when, whether this repo attaches it and its row files; `--json`. Guide: docs/team/client-folders.md.

- New op `doctor.last` (`lore doctor last`, `POST /v1/doctor/last`) reads each setup's last recorded doctor results and when they were taken, without running a check.
- Every warning and error of a doctor report is listed and counted: `findings[]` in `lore doctor --json` (check, status, level, detail, fix), counted in `counts` and in the text summary line, and the status is the worst of what the report lists, so it never reads "degraded" beside "0 warnings". A finding whose fix is one plain lore command (`lore render`, `lore sync`) can be run with `lore doctor fix <key>` (new op `doctor.fix`), which re-makes the report and runs only what it offers.
- Changing a solo setup's email keeps you one actor: the old key is kept under `aliases:` in config and in `key_aliases` on your actor rows, `actor show human:<old email>` still finds you, `actor list` shows one row with the current email, and a new machine with only the new email finds the same actor. Repo copies never carry an email.
- New ops `machine.reveal <lore_home|config_file|repo_lore>` and `machine.path.list`: show lore's folder, `config.yaml` or the repo's `.lore` in the file manager (Finder on macOS, Explorer on Windows, xdg-open on Linux). The target is a closed set, never a path, a missing file is `E_NOT_FOUND`, and over REST the reveal runs only for the local setup server, never for `lore api`.
- `lore config fmt [--dry-run]` rewrites `~/.lore/config.yaml` in block style when a list or mapping sits on one line (`setups: [{…}]` from a file saved before the block-style writer, which only a later write repaired), keeping comments and key order; `lore doctor` warns about such a file (`config_style`, naming the command and leaving the file as it is) and `lore doctor --fix` runs the rewrite.
- `lore config unset <key>` removes one key of `~/.lore/config.yaml` (a dotted path: `personal.store`, `identity`, `orgs.1`), keeping every other key, comment and the order; an emptied parent such as `personal:` goes too, `--dry-run` shows what would go, an absent key is `E_NOT_FOUND` naming `lore config list`, and a removal that would break a valid file is refused. Before it, the only way to drop `personal.store` was editing the file by hand (`config set personal.store ""` is refused).
- `lore setup list` lists **leftovers**: an identity or a personal store that `~/.lore/config.yaml` still holds but no setup uses (typically after a setup was purged without its clear options). New op `setup.leftovers.clear <identity|personal_store>` (`--dry-run`) clears one and refuses a key a setup uses again.
- `lore init` in a folder a setup applies to points the tools that setup picked at `.lore/LORE.md` (Claude Code gets `CLAUDE.md`) and says so ("tool files from setup work: CLAUDE.md"); with no setup, or a setup that picked no such tool, it wires the tool files the repo already has, else `AGENTS.md`; `--target` always wins. Files lore writes for the repo (`.gitignore`, the tool files, `.lore/` and its rows) are created readable by everyone (`0644`, folders `0755`), as the rest of a git work tree is.
- New ops `setup.folders` and `setup.browse` (names only, under the home folder): folder suggestions for a setup start with the folder you ran `lore setup` in and its git repo; gitconfig includeIf folders of another identity are marked and folders another setup covers say which.
- **The files are the truth.** Every shared row is one `_v: 2` JSON file under `.lore/data` (or in an attached store); the local SQLite cache is built from those files at run time and rebuilds itself when it is missing or damaged. Every write goes through one path: secret scan, validation, references, policy, the store, the cache, then the audit trail.
- **Stores:** git stores (a store branch, pushed at once, two clones converge) and folder stores (`file://`), attached per repo in `.lore/stores.yaml`; `--to` picks where a row is written.
- **`lore api`:** a local REST server on 127.0.0.1 with an OpenAPI description, built from the same operation list as the CLI, so every command has the same inputs, checks and errors over HTTP.
- **`lore migrate run`** converts v0.1.17 data (`_v: 1` rows, org links and roster, shared-database Mode B config) with `--dry-run`, `rollback`, a crash journal and `lore migrate unlock`; old config files are moved aside as `*.migrated`, never deleted (`~/.lore/identity.yaml` becomes `identity.yaml.migrated`).
- **Trash:** `delete` moves rows to the trash; `lore trash list|show|restore|purge`, `delete --purge` and the `trash.purge_on_delete` policy, `--from-history` to bring back a row from git history, and `lore batch undo` for a delete or create batch (an edit batch with later changes is refused whole with `E_STALE`).
- **Context budget:** `lore render` writes a small core into `.lore/LORE.md` inside a byte budget (must rules, critical and high hotfixes, the operating rules, an index of topics) with `--report`, `--check`, `--trend` and `.lore/LORE.full.md`; folder scopes get their own `LORE.md`; `lore context --for-file|--for-task|--topic|--topics|--for-prompt` fetches the rest; `lore setup --agent-hooks` wires it into Claude Code, Codex and Gemini CLI; `lore lint --context`; `lore pin set|unset`.
- **Tool profiles:** no tool is the default. `lore init` detects the tool file in the repo (or writes `AGENTS.md` when there is none) and saves the choice as the `context.targets` policy; profiles cover `CLAUDE.md`, `AGENTS.md`, `.cursor/rules/lore.mdc`, `GEMINI.md`, `.github/copilot-instructions.md` and user profiles.
- **Metadata, resources, variables and secret references:** `lore meta`, `lore resource`, `lore vars` and `${var:…}` references in any text field; `lore secrets` keeps references to a vault entry instead of the value.
- **Task trees and templates:** sub-tasks with `task split`, tree limits, `auto_start_parent`, task templates; time spans and estimates in hours and minutes.
- **Provenance and machines:** an origin block `_o` on every row (`--origin`), a `repos` row per checkout and machine rows; `lore repo fork --new-project`.
- `lore trash`, `lore sql` (read-only SQL over the cache with joins from the table definitions), `lore policy set|unset|show`, `lore cache prune`, `lore upgrade`, `lore hold claim`, `lore context --internal`, `--archived` on every list, `--color` and `--trace` on every command.
- Agent detection: the CLI records which coding agent ran a command, and `lore api` reads `X-Lore-Agent`, so `agents.person_only` applies on both.
- **Guided setup (in progress):** several setups per machine in a new `setups:` list of `~/.lore/config.yaml` (solo, member, admin; folder globs, GitHub account and ssh host alias, personal store, tools, secrets backend), `repo_setups`, and the keys `setup.idle_minutes`, `setup.open_browser`, `doctor.scan_depth`, `doctor.probe_timeout_s`; `lore config check` validates every entry and names the broken one. New tables `invites` (org roster store only), `setup_progress` and `known_repos` (this machine only), and the error codes `E_SETUP_NOT_FOUND`, `E_SETUP_AMBIGUOUS`, `E_SETUP_NAME_TAKEN`, `E_SETUP_ORG_MISMATCH`, `E_SETUP_NO_PERSONAL_STORE`, `E_SETUP_STEP_FAILED`, `E_SETUP_STEP_ORDER`, `E_INVITE_INVALID`, `E_INVITE_NOT_FOUND`, `E_INVITE_EXPIRED`, `E_INVITE_REVOKED`, `E_INVITE_USED`, `E_INVITE_EMAIL`, `E_STORE_NO_ACCESS`, `E_STORE_NO_WRITE`, `E_FIX_REFUSED`.
- **`lore skill install [--tool <profile>]... [--all] [--dry-run]`** installs the skill bundle embedded in the binary into each tool's skill folder (claude_code `~/.claude/skills/lore`, codex `~/.codex/skills/lore`, or a user profile's `skill_dir`), stamped `lore_version: <version>`; idempotent and atomic, keeps a `.bak-<date>` copy of a hand-edited file, and refuses a tool without a skill folder with `E_UNSUPPORTED`. **`lore skill status`** shows per tool the folder, the `lore_version`, hand edits and the version check (ok, older, newer, no version line, dev). Tool profiles gain an optional `skill_dir` (`context.profiles`).
- `lore upgrade` stamps the copied skill with the new version and prints `skills are older than lore {v}: lore skill install --all` when another tool's skill is older.
- Read-only onboarding probes: `git ls-remote`, a dry-run write test that pushes nothing, the store marker, `ssh -T`, `gh auth status` and repo/collaborator reads, `~/.ssh/config` reads and key fingerprints (`ssh-keygen -lf`, never the key's content), git identity, coding-tool and secrets-manager detection; each with its own timeout, at most 4 at once, and the setup's ssh host alias on every remote call.
- **`lore setup plan|check|apply|fix|list|show|use|edit|remove|join|repair`:** the guided setup ops over a step catalog (kind, identity, GitHub, personal store, join, team, tools, secrets, folders, this folder, summary): per-step answer validation and checks, the one write per step once no error-level check fails, progress kept until the summary, and repair that maps failing checks to their steps and runs only safe fixes with `--yes`. Fix commands are filled as argv only and refused with `E_FIX_REFUSED` when a value fails re-validation.
- **`lore doctor --all`** checks every setup on the machine (identity, GitHub key and login, stores, known repos, coding-tool skills and hooks, folder overlaps) and prints one block per setup with fixes; `--json` adds `setups`, `machine` and `counts`; `--fresh` skips the one-minute result cache; plain `lore doctor` adds a `[setup]` section for the active setup. Exit codes stay 0 healthy, 1 degraded (a warning or a check that could not run), 2 broken.
- **The local setup server:** `lore setup` on a terminal (or `lore setup web`, `lore onboard`) starts a local server on 127.0.0.1 at a random port: a one-time link, a session cookie with CSRF and Origin checks, a DNS-rebinding guard and a strict CSP; only the onboarding ops are reachable. A build from this source serves a plain page that lists the commands doing the same work (`lore setup plan|check|apply`, `lore doctor --all`); the prebuilt binaries serve the guided setup page. In a script, bare `lore setup` keeps the plain schema update; outside a repo it skips that step quietly.

### Changed

- **A project's format is the rule, never the binary's.** Each project records its format in the committed `.lore/data/_meta.json` (`format`, with `migrated_by` and `migrated_at`), shown by `lore doctor`, `lore where` and `lore migrate status`. In a project (or a shared store) still on the lore 0.1.17 format, this lore reads normally but every write, live landing, git hook, render and `lore fix` either leaves it as it is or refuses with one line, `<project> is on the lore 0.1.17 format; run lore migrate run to upgrade it (teammates need lore 0.1.18)` (`E_FORMAT_OLD`): no format-2 row ever reaches such a project, on any branch, local or pushed. The first-write auto-migrate is gone; only `lore migrate run` (or `lore fix --migrate`), run by a person, raises the format, records who and when, and leaves the signpost for 0.1.17 teammates in the same change. `lore fix`, `lore fix --all`, `lore doctor`, reads and link resolution never create `.lore/` in a repo with no lore data.
- **The personal store as a plain folder lives at `~/.lore/stores/_me`.** It sat at `~/.lore/stores/me`, beside the `stores/<owner>/<repo>` git clones, where it clashed with a git owner named `me`; GitHub and GitLab owner names cannot start with `_`. `lore store init me` with no url and the setup page's "A local folder" make `~/.lore/stores/_me`. The first command after the upgrade moves an existing `~/.lore/stores/me` folder store that `~/.lore/config.yaml` names as a personal store (`personal.store`, a setup's `personal_store`) to `stores/_me` under the config lock, points those keys at it and prints one line; a second run does nothing, and a git clone at `stores/me/<repo>` (owner `me`) is never touched. A personal store that is a git store keeps its usual `stores/<owner>/<repo>` clone. `lore where` names the folder as your personal store.
- **A store's address is printed as it is.** Without a terminal (a pipe, an agent's tool call) or with a CI variable set, lore printed `<redacted>` in place of every store url and org folder: the NAME and URL columns of `lore store list` for a plain `git@host:org/lore-x.git`, "matched by: link in <redacted>" in `lore whoami`, "registered in <redacted>", and the store url in errors and hints, so the person could not tell which store a message meant. A store's plain address and a local path are not secrets: they are now printed everywhere, in every output mode. Only a real secret inside a url is masked, and only that part: a password (the url's `user:<redacted>` part before the host), a token used as the user name (`<redacted>` before the host) and a credential query value (`?access_token=<redacted>`), by one rule (`repourl.Mask`) that every output uses. `lore whoami --share` is kept for older scripts and changes nothing.
- **Text output names at most 5 items of a list of ids.** A doctor finding listed every one of 84 `--supersedes` links on one line several thousand characters long. Every text output and error line (doctor findings included) now names the first 5 ids of such a list, then "… and N more (`lore doctor --json` lists all)" with the command that printed it; `--json` keeps every item. The SLA note of `lore doctor` no longer cuts its list in `--json` either.
- **A coding agent acts as its person.** A coding agent lore detects (Claude Code, Codex and the rest) may do anything its person tells it, and what it changes for the person is made as the person, while every row it writes still records the agent ("Ada via claude_code"). The team step of an admin setup run by the agent registers the person as the org's admin and roster member (it failed with "an agent cannot register actors"); `lore actor register`, `lore actor deactivate`, `lore agent start --label`, `lore team invite`, `lore store folder add`, `lore setup apply` and the human overrides `lore task cancel|reassign|revoke` and finishing another's claim pass for it; `lore gate approve` from the agent approves as the person; `lore resource kind edit --reviewed` from the agent marks the kind reviewed. An agent actor started with `lore agent start --label <l> --owner @<person>` acts for that owner. The one refusal left is an agent with no person behind it (an agent actor whose roster row names no owner), `E_INVALID_INPUT` or `E_REFUSED` with `needs_person`, naming `--owner @<person>`. A team opts into strictness by policy: `agents.may_manage_people false` refuses roster and profile changes, and `agents.person_only` lists any operation (`gate.approve`, `task.revoke`, `resource.kind.edit.reviewed`, `store.folder.add` …) an agent may not run. Approvals still come from an identity, never from `LORE_ACTOR`.
- `lore doctor` lists expired signal files as a note (they never changed the status; the next signals write drops them), not under warnings.

- With no setup and no `identity:`, lore shows git's `user.name` as your display name (the email's local part only when git has no name). Your actor id is unchanged, and actor copies are refreshed on the next write or `lore actor refresh`.
- `lore doctor`: the top-level `counts` (and status/ok) include the active setup's own checks, so the report never reads all ok while a setup check warns.
- `lore sync`: a row two people edited at once is reported once, under the store folder that holds it; the store's other folders say `held: waiting on <folder>'s conflict (<row>)` and are not marked as pushed. `lore sync status` lists them under `held pushes` (`data.store_held`), and `lore store doctor` names the folder that holds them.

### Fixed

- `lore secrets allow --file <path> --rule <rule> --match-hash <hash> --reason <why>` allows one finding in an ordinary repo file (a schema field named `password`, a test fixture); `lore secrets allow` with an id that is not a row names that form instead of only `E_INVALID_ID`. A first commit (no `HEAD`) is checked the same way, and a broken repo `.gitleaks.toml` is refused with its cause.
- An empty `--tasklist=` (and `--mission=`, `--plan=`) is `E_INVALID_INPUT` naming the flag, never a silent attach to an auto-created default list; when a task goes to the default list, one line says so.
- `lore member add` lowercases a person's handle (and derives one from the GitHub login or the email when none is given, skipping one already taken), saying so in one line; the GitHub login is kept as given; a handle with no letter is refused as a "person handle", not a "team handle". Every write command takes `--yes` (`lore member edit --yes` was "unknown flag"). Whoever starts the org (the admin setup) gets org role admin; `lore doctor` warns `org_admin_missing` for an org made before and `--fix` sets it. In an org store, lore's commits are signed by your git identity for the clone when it uses your org email (as your own commits there are), else by the org identity; docs/team/identity-and-stores.md says which wins.

- An audit trail write on a heavily loaded machine no longer fails with "database is locked" when other lore processes kept the lock longer than SQLite's 5-second wait: it keeps asking for the lock for up to a minute (or until the command is cancelled), so no audit record is lost.

## [0.1.17] - 2026-11-03

Lore for teams: everything in [LORE_TEAM_SPEC.md](LORE_TEAM_SPEC.md) phases P1–P4.

### Added

- **Team config** `~/.lore/config.yaml` (orgs, stores, patterns, repo choices, live/lease/agent settings) with `lore config check`, which names the line of every problem. The old TOML identity file is migrated to `~/.lore/identity.yaml` once; a malformed file names its line and is skipped, never silently replaced.
- **Orgs and identity:** each repo resolves to at most one org, by `LORE_ORG`, `lore org use`, a committed `.lore/org.yaml`, a store link or a remote pattern, and `lore whoami` says which rule decided it. Each org has its own identity; a repo that matches no org never borrows an org's identity. Remotes are read raw from git config (`url.insteadOf` rewrites are ignored).
- **Live rows:** any row can be shared with everyone at once on one hidden ref per repo (`refs/lore/live`, `--live` / `--no-live`; tasks, missions, handoffs and comments are live by default). Finished rows land on `main` by themselves, with `lore land`, or as a ride-along commit on your next push when `main` is protected. `lore live show|diff|log|restore|compact|purge` and `lore explain <id>` show and repair it; `--trace` prints every git command.
- **Merges:** lore's merge driver settles the file first (add/add, an edit beats a delete, tombstones), orders live scalars by a hybrid logical clock, and merges set-like lists (labels, approvers, team members, project links) without conflicts.
- **Stores:** separate lore-only repos for internal and personal notes (`lore store init|show|open|forget|doctor`, checked for a `lore-store.yaml` marker and refused if they hold code). `lore org link` ties a client repo to its internal project for the whole team without writing into the client repo; `lore org import` adopts a team's suggested config and registers you. `--to repo|<org>|<org>/<folder>|me` picks who a row is for; an unknown store folder is refused unless `--create` is given.
- **Leak guards:** a `commit-msg` hook, live writes, landings and `lore check pr-body` refuse internal ids, internal sentences (8 words or more) and secrets in a client repo, and fail closed when the store cannot be read. `lore check leaks --ci` checks structure only and names nothing internal. Output is redacted without a TTY or under a CI marker. `lore share` and `lore move` are the deliberate way across (new id, shows the text, asks first).
- **Cache and render outside the checkout:** external rows are cached in `~/.lore/cache`, internal context is rendered to `~/.lore/render` and imported through `CLAUDE.local.md`; `lore cache prune`, `lore context --internal`.
- **Roster:** `lore actor register|deactivate`, `lore team add|list`, `@handle` assignment to a person or a team, and `lore agent start` for one actor per agent session with its owner.
- **Agent coordination:** claims with a lease, a token and fencing on a second hidden ref (`refs/lore/signals`, always one commit): `lore task claim|next|heartbeat|release`, human overrides `revoke|reassign|cancel`, reclaim after expiry with an attempts limit, a ready queue that respects dependencies (`--after <id>[:merged]`), gates (`lore gate request|approve`, humans only), `lore inbox`, `lore handoff add --for`, `lore finding add`, `lore mission status`, `lore plan apply` (idempotent by key), `lore resource claim|release`, and a `Lore-Task:` commit trailer so a squash merge still counts as finishing the task. In client repos claims and work notes stay in the store; the client row carries only what the client should see.
- **Merged watching:** a done task is marked merged once its commit, its trailer or (optionally) its GitHub pull request is seen on `main`; `lore task merged` marks it by hand.
- Errors print their hint on the line under `ERROR:` and exit with the team error's own status (10–19).
- `task lore:trial:github` runs the team story (setup, org link, live tasks, landing, leak attempts, sharing, an agents mission with a crash, compaction, staging) against two real repos named by `LORE_TRIAL_CLIENT_REMOTE` and `LORE_TRIAL_STORE_REMOTE`, scans the client's clone for internal text after every step and prints a pass/fail table. Manual only; it wipes both repos first, and only when they are empty or carry the trial's marker ([docs](docs/team/real-repo-trial.md)).
- `lore sync install-action --auto` adds the pull request and push triggers to the workflow (they were the old default). `install-action --json` reports `auto` next to `manual`.

### Changed

- A plan file's `after:` takes the same `:done` / `:merged` suffixes as `--after`, so a plan can make a task in the same repo wait for a merge.
- `lore handoff add` takes `--for @handle` and `--task <id>`.
- `lore task add --tasklist` is optional; the project's default task list is used (created on demand).
- In a repo linked to a store, commands that run the lazy merged check print one warning line on stderr when the store cannot be reached, instead of saying nothing; the command still succeeds.
- `lore sync install-action` writes a workflow that runs only when started by hand (`workflow_dispatch`), so it never spends CI minutes on its own; the file's header says how to turn on automatic runs. `--manual` is still accepted (it is now the default) and `--auto` with `--manual` is refused.
- Re-running `lore sync install-action` without `--auto` or `--manual` keeps the installed workflow's triggers and branches, and the automatic lore-version update never changes triggers, so existing automatic workflows keep running.
- `lore rule list` hides archived rules; `--archived` shows them, marked `[archived]` (as `lore memory list` does).
- `lore identity set` needs an email: `alice@example.com`, `"Alice <alice@example.com>"`, or a name with `--key human:<email>`. A bare name is refused instead of being saved as a key that is not an email.
- Store branch names follow every rule of `git check-ref-format --branch` (a trailing `.`, control characters and `HEAD` are refused; so is `@`).

### Fixed

- Two clones creating the same store folder (for example two `lore actor register` runs from stale store fetches) no longer create two project rows: the folder's project id is derived from the store, branch and folder. Stores that already hold duplicates resolve through `_meta.json` with a warning instead of failing every `@handle` command with `E_AMBIGUOUS_PROJECT`.
- A command refused for an unknown `@handle` (`task add --assign`, `team add --members`, `agent start --owner`, `handoff add --for`, `task reassign`) writes nothing: no default task list, and no empty roster folder pushed to a store nobody has registered in yet.
- An `@handle` not found on a roster read from the fetch cache triggers one fresh store fetch and a retry before the refusal; a real miss on a store roster hints `lore sync` or `lore team list` (in a repo without an org it still says to register or add the team) instead of the live "landed on main" hint.
- After `lore.db` is rebuilt from `.lore/data` in a repo without an org, the next write reuses the person's actor row instead of adding a second actor with a random id.
- The same person on a second machine (new HOME, fresh clone) reuses their existing actor row, which a client repo holds only as a projection, instead of adding a new actor with a random id to the repo.
- `lore task note` in a repo linked to a store fails closed when the store or link status cannot be read (nothing printed, nothing written) instead of writing the note into this checkout; a plain repo with no org still writes it as before.
- `lore task note` on a task you do not hold writes the note where that task's notes live (the store project for a store task or an internal client task) and prints ✓ only after the write succeeded; it no longer prints ✓ and then fails with E_LEAK_BLOCKED.
- A merged task's `merged_at` is recorded once on the live ref and lands like any live row, instead of every clone writing its own copy into the working tree (which left checkouts dirty and blocked `git pull`). `lore task merged` takes the same path, and marking an already merged task writes nothing.
- `lore task done` without `--commit` no longer records a HEAD that is already on the default branch, so the task is not marked merged at once by mistake; the done line names the recorded commit.
- Reclaiming an expired task keeps the work branch the earlier holder recorded and pushed, instead of recording the reclaiming agent's own branch.
- `lore task list` filters store tasks like repo tasks (done and cancelled hidden by default; `--status`, `--mission`, `--assignee` and the other filters apply) and prints both in one line format, with the `[org/folder]` label on store rows.
- `lore sync` refreshes the store link index, so a teammate's new `lore org link` shows up at once.
- `lore org link --yes` says "created; pushed" when its push had to retry after a teammate's store write, instead of "already so, nothing changed".
- With a staging org chosen, `lore whoami` counts only the links on that store branch.
- `lore plan apply --help` describes the plan file format (it was cut off after one line).
- `lore share <id> --to repo` no longer refuses its own copy: the copy may carry the shared note's text (and only that note's); it is still refused when it quotes another internal note.
- The `pre-push` hook now runs the leak check on every file version and commit message the push sends to a client repo, so a `git commit --no-verify` no longer gets internal content onto the client's remote; it fails closed when the store cannot be read. `git push --no-verify` still skips every local check.
- Rows written to a client repo (`--to repo` for any kind) are leak-checked before they are written; a refusal prints no success line and writes nothing.
- The `E_LEAK_BLOCKED` hint names the repo row that leaks and how to move or delete it, instead of the internal note it matched.
- `LORE_TRACE=1` / `--trace` no longer prints the build machine's source paths for every database query; trace covers only the git commands for live rows.
- A `..` in `db_path` is refused with `E_BAD_PATH` and a hint naming `LORE_ALLOW_DB_PATH_OUTSIDE=1`, instead of `E_INTERNAL`.
- Landing messages name the real default branch (`default_branch:` or the remote's HEAD) instead of always saying "main".
- A fresh clone in a cloud-synced or network folder is refused with `E_NETWORK_FS` before anything is written; before, `.lore/lore.db` was built first.
- The docs-vs-CLI check treats only `$ ` lines in console examples as commands, so output that contains "; lore …" is no longer flagged.
- Finishing a task whose claim expired (`lore task done` by a person) now fails with the error, and writes nothing, if the done mark cannot be applied, instead of reporting success.
- `lore doctor` reports `--supersedes` links written by older versions (stored on the new row instead of the old one), and `lore doctor --fix` turns them round; running it again changes nothing. Links it cannot decide are listed and left as they are.
- A push that loses a race (`reference already exists`, a failed atomic transaction) is retried instead of reported as a refusal.
- Team writes fail closed: when the store cannot be reached or read, `lore task done`, `lore task cancel` and `lore finding add` stop with an error instead of writing the row into the client repo.
- `lore task list --mine` and `--claimed-by` stop with an error when the claims board cannot be read, instead of showing every task.
- A merged task that could not be recorded says so; "✓ merged" is printed only when the row was written. `lore store forget`, `store show` and `store doctor` report real failures instead of "nothing to forget", "not cloned" or "branch does not exist".
- A purge list that cannot be read stops the live apply, `lore live restore`, the landing pass and the merge driver with a clear error, so purged rows can no longer come back; a malformed purge list on one side of a merge no longer loses the other side's ids.
- Live rows are no longer dropped from lore.db when the live bookkeeping cannot be read after a refused write, and a live row file that cannot be read is no longer treated as having left live.
- `@team` handles resolve in a linked client repo, so assigning a task there to a team is refused with TEAM-030 as the spec says.
- `lore playbook add` and `lore prompt add` work again (new optional `--description`, defaulting to the title); `lore snapshot add` works again (new `--source`, default `manual`, checked against the known source kinds).
- `LORE_PROJECT_ID` and `LORE_REPO` are read when `--db` or `LORE_DB` is used outside a project folder.
- `--supersedes <id>` marks the old row: its `superseded_by_id` names the new row and a replaced decision becomes `superseded`. Unknown or already-replaced ids are refused and nothing is written.
- `lore doctor` no longer warns about a secret in a row that was deleted or edited clean: the recorded sync refusal is cleared when the row goes.
