# Story C — a 0.1.17 team, a CI runner, a big repo and the whole fleet

Test: `tests/stories/c_fleet_test.go` (`TestStoryCMixedFormat`, `TestStoryCCI`, `TestStoryCScaleFleet`).

## Who

Cleo, the admin (CTO), runs the new lore. A teammate still runs lore 0.1.17. A CI runner clones every repo fresh for each job. The repos: sync_go and auth (day-to-day projects lore 0.1.17 wrote: 176 rows each, `SmallShape`), hub (the big one: 5,500 rows lore 0.1.17 wrote, `HubShape`) and brick (code only, no lore data). Every repo is generated by `fixtures.go`; nothing is copied.

## Steps

1. Week 1, mixed versions. Cleo clones sync_go and auth and reads: `lore task list --all` shows every task lore 0.1.17 wrote, and `lore migrate status` says the project is on the lore 0.1.17 format and names `lore migrate run`.
2. Cleo tries to write (a memory, a task, a rule): each write is refused with the one line "… is on the lore 0.1.17 format; run lore migrate run to upgrade it".
3. Cleo runs `lore render`, `lore doctor --fix --yes`, `lore fix --yes` and `lore sync` in both repos.
4. Week 2, Cleo runs `lore migrate run` once in sync_go. It upgrades every row, commits nothing (lore never commits a code repo) and names the git line; Cleo runs that line.
5. CI on the old format: a depth-1 clone into a fresh HOME that was never set up for lore (`CI=true`). `lore check leaks --ci` refuses the 0.1.17 actor copies (their `stable_key`) and names `lore migrate run`; `task list`, `render --check`, `migrate status`, `doctor` answer.
6. Cleo migrates auth and pushes with her own `git push`. The next CI job's `lore check leaks --ci` passes, and the reads (`task list`, `search`, `render --check`, `migrate status`, `doctor`) answer.
7. Scale: in hub, `task list` (all 1,277 tasks), `memory list`, `search`, `whoami`, `migrate status`, `doctor` and a refused write each answer in time (wall times are logged; the bound is a generous 30 s so a loaded gate does not flake).
8. Fleet: with sync_go, hub and brick side by side, `lore doctor --all` (no setup on this machine) says it checked no repo and names `lore fix --all --dirs`; `lore fix --all --dirs <folder> --yes` names each format-1 repo and its `lore fix --migrate` line and skips brick.

## What must hold

- Old-format projects stay old until a person runs `lore migrate run`: after every command of steps 1-3, 7 and 8 every row file and `_meta.json` is still `"_v": 1` (`NewFormatFiles` is empty), and no tracked file changed (a 0.1.17 teammate's `git pull` never trips).
- `lore migrate run` keeps every row (each table has at least as many row files, `task list --all` the same count), rewrites every row, touches only the repo it ran in, and with the person's commit it is ONE commit.
- Nothing pushes without push/sync: no ref of any remote moves through steps 1-5, 7 and 8 (`migrate run` included: D-8); the only push is Cleo's own `git push` in step 6.
- A CI job changes nothing: the clone's files (`.git` config, hooks, info and the work tree) are identical before and after, and `git status --porcelain --ignored` is empty (no `lore.db-wal`).
- A repo without lore data stays byte-identical: brick after `doctor --all` and `fix --all`, and no `.lore` is created in it.
- Named flags: every hint printed in these steps uses named flags.
